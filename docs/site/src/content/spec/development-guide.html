Tests are discovered under //..., except manual or suite-excluded targets. Full and preflight allow two local test processes, run uncached and never retry failed tests. Preflight repeats setup and terminal tests three times. The SIGTERM check performs 40 cycles internally; guided connection entry repeats three times in lifecycle acceptance.

Partitions, special prerequisites and proof boundaries

The SSH partitions are lifecycle, files, reverse, shell, chains, reports, automation, follow and runs. Shell includes local forwarding and the focused aspect burrow sessions-check retained-shell lifecycle check; lifecycle includes SOCKS, manager/profile behavior, authentication, TUI and ownership. It also checks that download outcomes and evidence survive loss. The composed //core/cmd/burrow:connection_lab is a manual diagnostic, not an additional routine suite.

Workflow syntax is checked by digest-pinned actionlint. Skill-installer recovery uses Linux ptrace. Native client discovery is opt-in through aspect burrow agent-discovery, requires Bubblewrap and reports absent clients. Historical prototypes retain their own prerequisites and never establish production parity.

Public module boundary

All production capabilities belong to the single base burrow Hovel module. A second public identity requires an explicit owner requirement in the originating issue explaining why the base module cannot satisfy it. Internal Go packages, retained sessions and subprocesses do not justify another public module. The canonical production manifest is core/connection/hovel-module.yaml, packaged with the frontend and embedded for registration. Review registration and SDK entry points against this rule. Historical core/prototype_* modules and the test-only legacy-identity fixture are bounded evidence, never additional production packages.

The setup/profile checks cover the fresh catalog and shared SDK routing. The controlled SSH gate checks real base-module connections and profile writes, legacy-owner retention/collision refusal/explicit close, manual catalog transition and sibling/evidence preservation. PTY checks preserve Hovel’s review/confirmation flow with the consolidated module’s danger allowance.

Documentation authoring

Edit literal HTML fragments in docs/site/src/content/. Each begins with a burrow-doc JSON metadata comment and contains exactly one h1. Metadata generates the contents, chapter numbers, sidebar, and search. Change shared chrome in components/layouts; keep generated _site/ out of source control.

CI and PR preparation

PR and main CI use Ubuntu 24.04 with ten independent jobs, each capped at 15 minutes: portable, lifecycle, files, reverse, shell, chains, reports, automation, follow and runs. Each runs aspect burrow-check preflight SUITE; the same command reproduces that partition locally.

Build, test and assemble evidence

The portable partition builds packages, checks documentation and runs the portable tests, including normal first-launch and cache-reuse verification. It also runs aspect burrow-site stage and uploads docs-base. A separate required coverage job measures production Go code. After all partitions and coverage pass, the report job combines their matching evidence and produces docs-site. The shorter ci mode excludes Docker checks and is not the complete GitHub gate. Matrix fail-fast is disabled so independent failures remain visible. The required repository aggregate always runs and succeeds only when every partition, coverage collection and report assembly succeeds.

Review the exact commit

CI retains test logs, XML results, terminal captures and available phase/daemon logs in test-results-SUITE for 14 days, including after failure. Repeated local checks cannot reproduce every hosted-runner condition: wait for the PR check on its latest commit before requesting the owner’s merge approval. A failed required check must be diagnosed and fixed on that PR. Main requires an up-to-date PR and the GitHub Actions repository check, including for administrators; no approving review is required. The owner still explicitly authorizes the merge.

Optional constrained-runner rehearsal

For a constrained Linux rehearsal, run taskset -c 0,1 aspect burrow-check preflight (choose two CPUs available on your host). Use a fresh Bazel output base for this rehearsal: an already-running Bazel server keeps its original CPU affinity. With a fresh server, this limits child processes as well as test concurrency. The pinned Bazel, Go, Python, Node, pnpm, Hovel and SSH-image inputs remain the same; Docker, OpenSSH and the hosted OS are environmental prerequisites. PTY checks wait for decoded screen state and drain output through exit. Timing measurements include scheduling and decoder work; they are not standalone frontend benchmarks.

Hovel follow-up exception

The separate Hovel compatibility workflow runs aspect burrow-check preflight hovel: the WAL-lock regression and the two historical Docker-backed manager proofs tagged hovel-followup. Their failures remain visible but do not block the required Repository gate or Pages. This scoped release exception is tracked in #86; it does not fix the upstream runtime. All nine production SSH suites and normal startup verification remain required. The strict default aspect burrow-check still runs the upstream diagnostics. After an official fixed Hovel runtime is pinned and verified, remove the exception and return these targets to the required gate.

Public test and parity reports

The Reports tab publishes Burrow test results, production Go line coverage and operator interface parity. It is separate from collected SSH survey reports. The initial site build shows missing measurements explicitly. Attach real local evidence with:

aspect burrow-check preflight
aspect burrow-report coverage
aspect burrow-site stage
aspect burrow-report render

Keep the checkout unchanged across those commands. Evidence is stored under .report-input/ and binds the commit, source hashes, pins, operating environment and individual test repetitions. Rendering refuses stale or inconsistent evidence. A dirty checkout is labelled and supports local inspection; publication requires a clean matching source. After switching from individual partition runs to a full preflight, archive the older .report-input/ first; duplicate or stale inputs are refused rather than silently selected.

Coverage uses the existing six production Go test targets: interaction, forward control, daemon digest/RPC, online startup, audit and terminal host. It measures executable lines in core/cmd/burrow, core/connection, core/launch, core/reports, core/agent and core/terminal. Test code, test-only binaries, dependencies and prototypes are excluded. The separately run production SSH/CLI/PTY partitions establish behavior evidence but do not contribute to these counters. Unexecuted production code remains uncovered; unmeasured files remain listed. Raw LCOV, per-file numerators and denominators form the initial reproducible baseline, without an invented percentage target.

The canonical burrow capabilities inventory supplies human and agent routes, effects, reviews and schemas. docs/tools/docs/parity.json explicitly binds each capability to selected behavior checks and their scope. A new inventory capability without a binding fails the site build; the discovery check also rejects orphan human help commands. Reachability, documented JSON shapes and selected passing behavior are separate metrics. Descriptions alone are not complete schemas; optional MCP is not reported as typed MCP coverage. Passing a selected check is not exhaustive semantic equivalence.

aspect burrow-report publish requires all ten preflight partitions, measured coverage and matching clean site provenance. aspect burrow-report release additionally requires usable agent routes and passing selected behavior for every capability, and remains failing while MVP 5 parity is incomplete. Owner acceptance remains separate. Advisory Hovel #86 results never replace a required check.

Publishing

The portable CI partition stages docs-base. Every partition preserves its commit-bound report input, including failed-test diagnostics, for 14 days. A separate coverage job retains its LCOV and results. Only after all required jobs pass does the report job assemble the site and evidence; available completed advisory results for that exact commit are attached, otherwise the report says missing. It uploads docs-site after publication validation. Failed required jobs keep diagnostics and cannot produce an eligible site.

Pages promotes that exact artifact only after the complete Repository workflow succeeds on a main push. Manual dispatch is main-only and finds a successful Repository push run for its exact commit. Both paths download the existing site, verify its report source and all artifact hashes through aspect burrow-report verify SHA, and skip deployment if main has advanced. They do not rebuild the site or rerun application tests. Missing, altered or mismatched artifacts fail verification. GitHub Pages must be enabled separately; a private repository does not itself make its Pages site private.
