Development guide

Aspect CLI is the entry point for builds, tests, formatting, packaging, and documentation. Run aspect help to discover the checked-in AXL tasks.

aspect burrow-check preflight
aspect burrow-site build
aspect burrow-site check
aspect burrow-site stage

The full gate builds the production package, metadata and prototype packages, checks the generated documentation, and exercises SDK protocol, daemon reuse and production SSH behavior. It discovers routine declared tests under //..., so new tests enter the gate automatically unless explicitly tagged manual or excluded by the selected suite. A digest-pinned actionlint checks every GitHub workflow’s syntax and expressions as //:workflow_test. Test results are uncached and failed tests are not retried. Full and preflight gates allow at most two local test processes. aspect burrow-check preflight repeats only setup_test and terminal_test three times, requiring every repetition to pass. The SIGTERM regression exercises 40 cycles inside its unit check, and guided connection entry repeats three times within lifecycle acceptance; other test targets run once. The production SSH fixture uses a digest-pinned disposable OpenSSH Docker container; Docker and local OpenSSH client tools are required. aspect burrow-check ci builds production packages and prototypes and runs portable checks without Docker. Run aspect burrow ssh-check for all nine production SSH partitions: lifecycle, files, reverse, shell, chains, reports, automation, follow and runs. These partitions preserve every routine assertion from the composed lab. The shell partition includes local forwarding; reverse forwarding and file workflows have separate partitions. Lifecycle covers SOCKS, manager/profile behavior, authentication, TUI flows and ownership. It seeds a real download and retains the assertions that download outcomes, totals and evidence survive connection and owner loss. The original //core/cmd/burrow:connection_lab remains an explicitly requested manual diagnostic target and is excluded from routine discovery. The earlier transport proof retains its historical host-binary prerequisites and is runnable separately. Passing observations of known gaps do not establish production SSH parity. Staging writes the generated artifact to _site/.

Public module boundary

All production capabilities belong to the single base burrow Hovel module. A second public identity requires an explicit owner requirement in the originating issue explaining why the base module cannot satisfy it. Internal Go packages, retained sessions and subprocesses do not justify another public module. The canonical production manifest is core/connection/hovel-module.yaml, packaged with the frontend and embedded for registration. Review registration and SDK entry points against this rule. Historical core/prototype_* modules and the test-only legacy-identity fixture are bounded evidence, never additional production packages.

The setup/profile checks cover the fresh catalog and shared SDK routing. The controlled SSH gate checks real base-module connections and profile writes, legacy-owner retention/collision refusal/explicit close, manual catalog transition and sibling/evidence preservation. PTY checks preserve Hovel’s review/confirmation flow with the consolidated module’s danger allowance.

Documentation authoring

Edit literal HTML fragments in docs/site/src/content/. Each begins with a burrow-doc JSON metadata comment and contains exactly one h1. Metadata generates the contents, chapter numbers, sidebar, and search. Change shared chrome in components/layouts; keep generated _site/ out of source control.

CI and PR preparation

PR and main CI use Ubuntu 24.04 with ten independent jobs, each capped at 15 minutes: portable, lifecycle, files, reverse, shell, chains, reports, automation, follow and runs. Each runs aspect burrow-check preflight SUITE; the same command reproduces that partition locally. The portable partition builds packages, checks documentation and runs the portable tests, including normal first-launch and cache-reuse verification. It also runs aspect burrow-site stage and uploads docs-site. The shorter ci mode excludes Docker checks and is not the complete GitHub gate. Matrix fail-fast is disabled so independent failures remain visible. The required repository aggregate always runs and succeeds only when every partition succeeds. CI retains test logs, XML results, terminal captures and available phase/daemon logs in test-results-SUITE for 14 days, including after failure. Repeated local checks cannot reproduce every hosted-runner condition: wait for the PR check on its latest commit before requesting the owner’s merge approval. A failed required check must be diagnosed and fixed on that PR. Main requires an up-to-date PR and the GitHub Actions repository check, including for administrators; no approving review is required. The owner still explicitly authorizes the merge.

For a constrained Linux rehearsal, run taskset -c 0,1 aspect burrow-check preflight (choose two CPUs available on your host). Use a fresh Bazel output base for this rehearsal: an already-running Bazel server keeps its original CPU affinity. With a fresh server, this limits child processes as well as test concurrency. The pinned Bazel, Go, Python, Node, pnpm, Hovel and SSH-image inputs remain the same; Docker, OpenSSH and the hosted OS are environmental prerequisites. PTY checks wait for decoded screen state and drain output through exit. Timing measurements include scheduling and decoder work; they are not standalone frontend benchmarks.

Hovel follow-up exception

The separate Hovel compatibility workflow runs aspect burrow-check preflight hovel: the WAL-lock regression and the two historical Docker-backed manager proofs tagged hovel-followup. Their failures remain visible but do not block the required Repository gate or Pages. This scoped release exception is tracked in #86; it does not fix the upstream runtime. All nine production SSH suites and normal startup verification remain required. The strict default aspect burrow-check still runs the upstream diagnostics. After an official fixed Hovel runtime is pinned and verified, remove the exception and return these targets to the required gate.

Publishing

The portable CI job validates and stages the site, retaining docs-site for 14 days. Pages promotes that exact artifact only after the complete Repository workflow succeeds on a main push. Manual dispatch is main-only and finds a successful Repository push run for its exact commit, then downloads that run’s existing artifact without rebuilding or rerunning tests. A missing successful run or unavailable artifact fails deployment preparation. Before deployment, both paths check that the artifact’s commit is still current on main and skip superseded runs. GitHub Pages must be enabled separately in repository settings. A private repository does not by itself make its Pages site private.
