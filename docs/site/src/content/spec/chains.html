SSH and tunnel chains

Hovel chains can establish a named SSH connection in Burrow or make a bounded HTTP request through an existing forward. Both operations use the single burrow@0.1.0 module, its retained connection owner and Hovel's normal planning, confirmation and artifact contracts.

Each export currently contains one configured operation. Connection creation and existing-tunnel consumption are separate flows; Burrow does not generate an upload → start server → connect → create tunnels pipeline.

Jump to: connection flow · consumer flow · TUI SSH handoff · TUI HTTP · CLI Dropbear · CLI password · embedded Hovel · CLI HTTP/export · L/R/SOCKS examples · headless execution · cleanup and troubleshooting

What happens when a chain creates an SSH connection?

The target needs its SSH server and account; it does not need Hovel or Burrow installed. The module runs locally, and the retained manager owns the local SSH client. Hovel's automation chain is distinct from an SSH jump-host chain. Use the existing --jump [USER@]HOST[:PORT][,...] option when the connection needs network hops.

What happens when a chain uses a tunnel?

chain select and export do not send the HTTP request. They do verify existing resources; for reverse tunnels this can query remote listener metadata through the existing master. A missing or changed resource causes refusal, never a replacement login or silently selected same-port listener.

Create a connection from a chain

The target must already run an SSH server, such as OpenSSH or Dropbear. Its account must accept the selected key, agent or password authentication. Exporting a chain resolves and records non-secret connection settings without authenticating:

burrow --workspace /absolute/workspace chain connect target target.example --user tester \
  --port 2222 --key /absolute/path/to/private-key > connect.chain.json
hovel throw connect.chain.json --workspace /absolute/workspace \
  --daemon-endpoint /absolute/workspace/hoveld.sock --allow-dangerous --json

Use Burrow's installed Hovel executable, or enter the equivalent throw /absolute/connect.chain.json --allow-dangerous --json in the workspace's embedded Hovel CLI. Confirm the plan. Headless execution needs an existing matching confirmation or an explicitly selected --now; that option does not bypass dangerous-module or launch-key restrictions. JSON mode does not promise JSON-only failure output.

An unattended key/agent chain waits up to 30 seconds for authentication; a private password/passphrase frontend uses the existing two-minute authentication limit. Success returns the connection's name, session, owner generation and creation identity. The live connection appears in Burrow's management inventory and supports its normal commands:

The execution path is: confirmed Hovel throw → local base Burrow module → retained workspace connection manager → local OpenSSH client/master → target SSH server. Hovel and Burrow do not need to run on the target. The manager owns the SSH connection, so completion of the throw or quitting the TUI with Keep running does not end that connection.

inspect target
shell target
run now target -- /usr/bin/id
close target

The connection remains available after the chain finishes. Closing it ends Burrow's master and dependent resources; it does not stop or uninstall the target's pre-existing SSH server. Authentication failure or timeout attempts cleanup of that exact connection and reports uncertainty if cleanup cannot be confirmed. Existing names and unknown reservations are refused, including replay of a chain while its connection is still live. Reconnect remains explicit.

chain connect also accepts --password, --prompt, --agent, --ssh-config and --jump. Both --password and --password PASSWORD select password-only authentication for the target. Bare --password opens a hidden prompt after Hovel confirmation; --password PASSWORD supplies the value automatically without a password popup. Use --key PATH --prompt for an encrypted key. Implicit proxy creation remains excluded. Private keys remain local; exported chains contain paths and authentication preferences, never key contents or passwords. The existing owner-approved LazySSH host-trust settings apply. Export again if the resolved SSH configuration or Burrow build changes.

A Dropbear deployment provider is not required to connect to a running server. Preparing a binary, uploading it, configuring authorization, launching it and owning its remote cleanup are separate deployment work, requiring an existing authorized delivery/execution path. Dropbear alone does not supply initial target access, and a bare Dropbear server needs an external SFTP server for Burrow's file workflows. The current compatibility check proves SSH authentication and command execution, not all Dropbear deployment, PTY or file combinations.

Choose and consume an existing tunnel

Create the connection and forward or SOCKS proxy first. Select the connection, then query its authoritative live inventory. In the following examples, replace gateway/CREATION with a complete ID returned by selection or Tab completion:

chain select gateway
chain http gateway gateway/CREATION http://internal.example:8080/health
chain export gateway gateway/CREATION http://internal.example:8080/health

chain http presents a review. The TUI uses its existing confirmation dialog; Escape cancels without a request. The CLI returns a digest: repeat with --review DIGEST --yes to bind approval to that exact selection. chain export stages and prepares Hovel in the TUI; the CLI returns JSON for redirection. Both export paths preserve the exact selection without sending the HTTP request.

Loopback defaults and explicitly requested bind addresses are preserved; wildcard listeners are contacted through the corresponding loopback address. Inventory and use recheck the retained master and listener. Server-forced reverse exposure remains subject to the existing post-allocation observation and cleanup limitation.

Results and lifetime

The HTTP operation supports one GET over plain HTTP, an eight-second consumer context and at most 1 MiB of response body; preflight and cleanup also use bounded owner checks. It does not follow redirects, inherit ambient HTTP proxies, accept proxy credentials, or support authenticated requests, query strings or TLS. All request fields are recorded: never place secrets in URL paths. A complete HTTP exchange records the actual status, including 3xx/4xx/5xx; that establishes transport success, not application health.

Hovel stores a JSON artifact with the exact non-secret tunnel selection, request URL, run correlation, HTTP status, byte count and response SHA256. Body and header contents are discarded. Timeout, malformed/incomplete response or a body over the bound produces a failed result. Failure to store evidence must not be reported as successful collection. Inspect artifacts through Hovel after the operation, including when a caller disconnected after dispatch; do not automatically retry a request whose outcome is uncertain.

Selection binds workspace, manager session/generation, connection creation and tunnel creation. Removing and recreating the same port produces a different ID. Missing selections, changed identities, removed tunnels, closed connections and master loss fail without login, provisioning or fallback. Concurrent consumers retain shared forwarding; ending a consumer or its frontend does not remove it. Explicit listener removal or connection close waits for admitted bounded consumers, then performs the existing cleanup. Collected artifacts survive teardown.

This is the accepted owner-mediated HTTP consumer, not transparent routing of arbitrary Hovel modules or a generic Mesh bridge. Direct same-user manipulation of control sockets remains outside the owner's inventory contract. The pinned public session-command workaround from issue #34 remains nonblocking; session commands themselves do not certify throw approval. Use the confirmed chain/module route for execution.

Walkthrough · From Burrow to Hovel to active SSH

Starting point: an SSH server is already listening at 192.168.10.50:22. You have its account username and either a local private key or its password. Open the intended workspace in Burrow. The following commands belong in the Burrow management prompt.

The inline popup shows chain connect NAME HOST --user USER [options] and a complete example while you type. target is an example connection name; choose your own label, then enter the SSH host and username. Completion offers the required username before optional flags.

  1. Choose the account and authentication explicitly. Port 22 is the default; including it can make a copied example clearer:

    chain connect target 192.168.10.50 --user alice --port 22 --password

    For a key instead:

    chain connect target 192.168.10.50 --user alice --port 22 --key ~/.ssh/id_ed25519

    These are alternatives for the same connection name. Do not run both while that name is occupied. The older positional username remains accepted for existing scripts; --user is the recommended form.

  2. Press Enter in Burrow. It resolves the settings, writes a unique private chain file and switches to the existing Hovel tab, opening one if needed. This stage performs local preparation only. It does not contact the target to authenticate.

  3. At an empty Hovel command prompt, Burrow selects the local burrow operation and burrow-chain context if necessary. These selections make Hovel's live chain logs visible. It then prepares a command like:

    throw /absolute/workspace/connect-target-123456789.chain.json --allow-dangerous

    The filename is generated, so yours will differ. There is no --now or --json in this TUI command. Burrow does not submit the throw or answer its confirmation.

  4. Press Enter in Hovel. Read its normal plan, including the endpoint, username, authentication settings and module. Type yes at Hovel's confirmation if it matches your intention. Any Hovel launch-key policy still applies.

  5. With bare --password, a hidden Burrow field appears only when SSH asks. Its title identifies the connection and account. Type the password and press Enter. The dialog closes and Hovel remains visible while authentication finishes. Passwords are excluded from terminal output, command history, JSON, logs and artifacts. The target uses password authentication even if a default key or agent is available. Jump hosts retain their own configured authentication.

  6. Wait for Hovel's result. Read whether the module succeeded; a throw finishing alone is not proof that every step succeeded. For a successful connection result, press Alt+B to see target in Active SSH Connections. Use:

    inspect target
shell target

    The connection is daemon-owned. It stays available after the chain finishes or you quit Burrow with Keep running.

What if Hovel already contains a command or confirmation?

Burrow stages the JSON and switches to Hovel, preserving that input. It displays “Hovel input retained” and leaves the complete throw command in Burrow's command output, reachable with Alt+B. Finish or cancel the existing Hovel interaction before entering the staged command. Typing while Hovel is starting also cancels the automatic prefill. An exited CLI requires its normal explicit restart; no command is replayed automatically.

How long is a password chain usable?

A password/passphrase export references a one-use private frontend endpoint. Keep the exporting Burrow process open and start the confirmed chain within ten minutes. Authentication then uses Burrow's existing two-minute prompt limit. Closing the frontend or cancelling the secret field cancels that exact pending authentication and attempts cleanup; inspect the result if cleanup is uncertain. A completed connection survives frontend exit. Regenerate an expired or already-used password chain. One pending interactive chain is supported per TUI at a time. After rejecting a Hovel plan, press Ctrl+C in Hovel to cancel its waiting private frontend before staging another interactive chain. Lists and independent connection/tunnel controls remain available while it waits.

For encrypted keys, use chain connect target 192.168.10.50 --user alice --key ~/.ssh/id_ed25519 --prompt. For unencrypted keys or a ready agent, omit --prompt. To supply the password automatically, enter chain connect target 192.168.10.50 --user alice --password PASSWORD, replacing the placeholder. Hovel still reviews and confirms the staged throw. Inline text is visible while typed; Up recalls the command with bare --password, without the supplied value.

Walkthrough 1 · Review and run a request in the TUI

Starting point: the active workspace contains a connected SSH connection named target, and its SSH server can reach an HTTP service at internal.example:8080. Replace the example destination with your own. These commands go in Burrow's management prompt.

  1. Press Alt+B to select Burrow. Create a local forward using the existing command:

    tunnel create target forward 18080 internal.example 8080

    Review the connection, local listener and remote destination. Choose Proceed and press Enter. Escape or Cancel creates nothing. If the intended forward already exists, use it instead of creating a duplicate.

  2. Read the current selection:

    chain select target

    Find the L entry whose listener is 127.0.0.1:18080 and destination is internal.example:8080. Copy its complete ID or use Tab completion in the next command. CREATION_ID below is a placeholder, not a literal value.

  3. Request an HTTP review:

    chain http target target/CREATION_ID http://internal.example:8080/health

    The URL names the fixed destination, not the local listener. The recap includes connection, full tunnel ID, direction, bind, destination, URL and limits. No GET has been sent yet.

  4. Try Escape to cancel. Submit the command again, move focus from Cancel to Proceed with Tab or the arrow keys, and press Enter. Approval is bound to that exact reviewed selection.

  5. Read the result in command output. Use PgUp/PgDn to scroll. Inspect state, statusCode, bytes and sha256. Run inspect target and chain select target to confirm that the connection and forward remain.

Expected outcome: one GET through the selected forward, a Hovel result artifact, and a still-running SSH connection and listener. A complete HTTP 404 or 500 establishes transport completion, not application health. F1 opens help; NO_COLOR retains controls and text.

Walkthrough 2 · Connect to running Dropbear from the shell CLI

Starting point: Dropbear already listens on your target, an existing account accepts your key, and the connection name target is unused. The same steps apply to OpenSSH. Replace the documentation address 192.0.2.10, sample account and paths before running commands.

Set these variables in your local shell, not in either application prompt. The key or unlocked agent must be accessible to the daemon.

CHAIN_WORKSPACE=/home/operator/burrow-lab
CHAIN_KEY=/home/operator/.ssh/lab_ed25519
CHAIN_HOVEL="${XDG_CACHE_HOME:-$HOME/.cache}/burrow/hovel/0.4.2/hovel"
burrow --workspace "$CHAIN_WORKSPACE" status

Export without authenticating

burrow --workspace "$CHAIN_WORKSPACE" chain connect target 192.0.2.10 --user tester \
  --port 2222 --key "$CHAIN_KEY" > "$CHAIN_WORKSPACE/connect-target.chain.json"

This writes the configured chain, resolved SSH settings and review digest. It does not authenticate, upload Dropbear, configure an account or start the server. Inspect the generated file; it contains paths and configuration, never private-key contents or passwords.

Review and execute in Hovel

  --workspace "$CHAIN_WORKSPACE" \
  --daemon-endpoint "$CHAIN_WORKSPACE/hoveld.sock" \

Read Hovel's plan and answer its confirmation prompt. --allow-dangerous permits the base module's capability classification; it does not itself approve execution. Launch-key requirements remain in force. Without confirmation no connection is created.

After approval, Burrow verifies the workspace, build and resolved SSH settings, refuses an existing name reservation, obtains the retained manager and starts SSH. It waits up to 30 seconds for observed connected state. A dispatch acknowledgement alone is not success.

Find and use the registered connection

burrow --workspace "$CHAIN_WORKSPACE" connections
burrow --workspace "$CHAIN_WORKSPACE" inspect target
burrow --workspace "$CHAIN_WORKSPACE" shell target

Inspection should show connected. A TUI on the same workspace also displays the connection: use shell target or the existing reviewed run now target -- /usr/bin/id there. The chain creates a connection; opening a shell is a separate action.

Expected outcome: Hovel retains a connection artifact and Burrow owns a live SSH master. Dropbear remains independently running. Replaying the creation chain against the reserved name fails instead of adopting or reconnecting it.

Walkthrough · Password authentication from the CLI

This keeps JSON output usable by scripts while a human supplies the secret through a controlling terminal. Use two local terminals on the same machine and workspace. A key/agent export exits after printing JSON; a password/passphrase export stays open until the confirmed chain's authentication finishes or is cancelled.

  1. In terminal A, export the chain and keep this process open:

    umask 077
burrow --workspace /absolute/workspace chain connect target 192.168.10.50 \
  --user alice --port 22 --password > /absolute/workspace/password.chain.json

    Stderr reports that JSON is ready. Nothing has authenticated yet. Stdout contains only the chain JSON.

  2. In terminal B, run the exported chain with the pinned Hovel executable. Review and confirm normally:

    HOVEL_BIN="${XDG_CACHE_HOME:-$HOME/.cache}/burrow/hovel/0.4.2/hovel"
"$HOVEL_BIN" throw /absolute/workspace/password.chain.json \
  --workspace /absolute/workspace --daemon-endpoint /absolute/workspace/hoveld.sock \
  --allow-dangerous --json

  3. Terminal A shows the hidden password field after Hovel confirms. Enter the password there. Terminal B receives the chain result; terminal A exits after authentication. Cancellation uses Ctrl+C in terminal A.

  4. Check the live connection:

    burrow --workspace /absolute/workspace inspect target

    The JSON should show state: connected. Reopen the TUI on that workspace, or run another supported Burrow command against target.

Automatic password with no controlling terminal

PASSWORD below is a placeholder. The server and account must already exist. In process A, export using a supplied value; leave that process alive:

umask 077
burrow --workspace /absolute/workspace chain connect target 192.168.10.50 \
  --user alice --port 22 --password PASSWORD > /absolute/workspace/password.chain.json

Wait for “Chain JSON exported” on stderr before starting process B. After reviewing the generated operation, an unattended caller can explicitly approve its throw:

HOVEL_BIN="${XDG_CACHE_HOME:-$HOME/.cache}/burrow/hovel/0.4.2/hovel"
"$HOVEL_BIN" throw /absolute/workspace/password.chain.json \
  --workspace /absolute/workspace --daemon-endpoint /absolute/workspace/hoveld.sock \
  --allow-dangerous --now --json

No password popup or controlling terminal is required. Process A exits when authentication completes; stdout remains only chain JSON and status goes to stderr. The broker is one-use and expires after ten minutes. Keep process A alive until the result arrives. A saved file cannot recreate the password after that process exits. Explicit Hovel approval is still required; supplying the password does not approve a connection.

Quote passwords containing spaces. Use --password=VALUE for a leading dash or an empty password. Values are limited to 4,096 bytes without NUL, CR or LF. They stay in frontend memory and out of Burrow command history, logs, previews, saved profiles, Hovel config/artifacts and child process arguments/environment. Literal CLI passwords remain visible in the original process arguments and may enter the invoking shell's history. Inline TUI commands are visible while typed. In the TUI, Up recalls the connection command with a bare --password flag for fresh hidden entry; supplied password values are never recalled. Choose the bare flag for hidden entry.

The automatic value answers only the target's password request, once. Wrong passwords fail and attempt exact-owner cleanup. Jump hosts keep their configured authentication; if a jump asks for a password or passphrase, the automatic target value is refused. Use available jump keys/agents or bare interactive entry. Direct CLI connections also accept connect NAME HOST --user USER --password PASSWORD --yes; omit --yes for a passive review.

Walkthrough 5 · Follow local, reverse and SOCKS traffic

Local means the Burrow/SSH-client machine. Remote means the SSH-server machine. These examples assume the HTTP services already exist; none of these commands starts a service.

Local forward: a fixed service reachable from the SSH server

tunnel create target forward 18080 internal.example 8080
chain select target
chain http target target/LOCAL_CREATION_ID http://internal.example:8080/health

The URL must name internal.example:8080, not 127.0.0.1:18080. Changing the URL does not retarget this forward. Its path selects the HTTP resource at the fixed destination.

Reverse forward: a local service reached from the remote listener

Suppose a service already listens on 127.0.0.1:8080 on the Burrow machine. Request a random high reverse port on the server:

tunnel create target reverse 0 127.0.0.1 8080
chain select target
chain http target target/REVERSE_CREATION_ID http://127.0.0.1:8080/health

The URL uses destination port 8080, not the allocated remote listener port. A direct request to the local HTTP service would not prove the reverse route. The server must permit the diagnostic forwarding channel and expose verified Linux listener metadata. No remote Python or HTTP client is installed.

SOCKS: choose each destination and resolve names remotely

proxy create target 1080
chain select target
chain http target target/SOCKS_CREATION_ID http://internal.example:8080/health

SOCKS has no fixed destination, so each reviewed URL may choose a different host and port. Failure does not fall back to local DNS or an ambient HTTP proxy. Use the complete SOCKS creation ID from chain select; the displayed proxy port alone is not its identity.

Walkthrough 6 · Explicit headless approval and evidence

After inspecting the exported operation, you may deliberately choose a noninteractive throw:

"$CHAIN_HOVEL" throw "$CHAIN_WORKSPACE/health.chain.json" \
  --workspace "$CHAIN_WORKSPACE" \
  --daemon-endpoint "$CHAIN_WORKSPACE/hoveld.sock" \
  --allow-dangerous --now --json > "$CHAIN_WORKSPACE/health.throw.json" \
  2> "$CHAIN_WORKSPACE/health.throw.err"
CHAIN_STATUS=$?

--now is an explicit approval choice recorded by Hovel, not a bypass of dangerous-module or launch-key restrictions. A matching existing confirmation is another Hovel route. Without either, JSON mode may still print an interactive prompt and fail at EOF.

Keep stdout, stderr and the process status. Check status first, then the Hovel step's state, then parse its summary. For HTTP, inspect the result's state and actual statusCode; process success is not an application-health assertion. Failure output is not universally JSON. See Local tools and automation for the surrounding result-handling contract.

What is in the exported file?

The file has Hovel's API version, kind: Chain, metadata, configured mode, one step using module:burrow@0.1.0, a local target label and string configuration. The default exported name is burrow-chain. The local label executes the module locally; the SSH endpoint is in connection settings.

Connection exports use action: chain-connect, workspace, build, settings, resolved SSH configuration and digest. HTTP exports use action: tunnel-http, workspace, build, manager session/generation, complete tunnel binding, URL and digest. Generate these fields through Burrow instead of hand-editing IDs. Changed build, settings or resources may require another export.

How to read HTTP evidence

A tunnel-http artifact contains consumer runID, exact selection, url, state, statusCode, bytes and a sha256 for a complete bounded response. Selection includes connection creation, manager session/generation and the tunnel's creation run. Response bodies and headers are discarded.

A complete 302 is recorded without following Location. A complete 404/500 can have state: succeeded because the exchange completed. Timeout, incomplete response or a body over 1 MiB fails and receives a failed audit outcome. Refusal before traffic can produce a Hovel error without an HTTP artifact. Evidence-storage failure must not be treated as successful collection.

Request URLs are limited to 2,048 bytes and exclude credentials, query strings and fragments. Request fields are recorded, so paths must not contain secrets. Responses are bounded to 1 MiB of body and 32 KiB of headers; there is no automatic decompression. Only plain HTTP GET is supported, with no custom authentication or TLS.

Retained manager does not support password authentication

Restarting only the TUI can leave an older connection manager running. Burrow checks its advertised password support before staging or dispatch, independently of the executable hash. Inspect the same workspace, then explicitly review retirement if intended:

burrow --workspace /absolute/workspace connections
burrow --workspace /absolute/workspace restart

The restart review covers that manager and its connections, including connections added concurrently. Confirm only when you intend to close them. An empty inventory means it currently owns no connections. The daemon, saved settings, evidence and separate retained script sessions remain. Avoid make restart for inspection: it supplies --yes. Reopen Burrow and stage a fresh chain after retirement; no failed connection is retried automatically. A Hovel throw marked completed can still contain a failed module; inspect the step's state.

Connection name already reserved

Inspect the name. Use the intended existing connection, choose another unused name, or explicitly close/recover the old resource before creating another. Unknown reservations require investigation; the chain will not force-delete or adopt them.

Saved chain now refuses its selection

Check workspace, build, manager and complete creation IDs. Owner restart, connection recreation, tunnel recreation or changed resolved SSH settings can invalidate the export. Re-establish resources explicitly and export again. A matching port is insufficient.

SSH works but HTTP fails

Check direction, fixed destination, service availability and forwarding permissions. SOCKS names must resolve from the SSH server. Reverse consumption also needs the server-origin channel and readable Linux listener metadata. Inspect time/response limits and Hovel's failure before retrying.

Caller disappeared or evidence storage failed

Do not infer cancellation. Inspect Hovel history, artifacts and current resource state in the same workspace. Traffic may have happened without the caller receiving its result. Repeating an HTTP chain sends another GET.

Hovel reports “database is locked”

The pinned Hovel CLI can refuse simultaneous startup against one workspace's SQLite store. This was observed during the concurrency check.
