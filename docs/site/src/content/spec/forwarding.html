Local SSH forwarding

Create a local TCP listener on an existing named connection. Commands work in Burrow management and through burrow --workspace /absolute/workspace COMMAND. Required endpoints come first:

tunnel create gateway forward 8080 localhost 80
tunnel create gateway forward 8080 localhost 80 --yes
tunc gateway l 8080 localhost 80
tunnel list
tunnel check gateway/CREATION_ID
tunnel remove gateway/CREATION_ID
tund gateway/CREATION_ID --yes

In the TUI, the first command opens the existing confirmation recap; Escape or Cancel creates nothing. The CLI returns a review without --yes. To bind approval to that exact review, repeat its --review HASH with --yes. The listening endpoint defaults to 127.0.0.1; select another literal address explicitly, such as 0.0.0.0:8080. Broader binds expose the forwarded service to other hosts. The destination is reached from the SSH server. IPv6 listening endpoints use brackets, for example [::1]:8080; the separate destination HOST argument uses a bare address, such as ::1. TCP ports must be 1–65535.

tunc CONNECTION l LISTEN HOST PORT is an alias for tunnel create CONNECTION forward LISTEN HOST PORT; tund ID aliases tunnel remove ID. Both spellings use the same validation and confirmation. Tab after tunnel create or tunc offers live connection names from the current workspace, not saved profiles or closed connections. Reverse forwarding is not implemented yet.

The TUNNELS table retains the ID, owning connection, direction, listening endpoint, destination and observed state. Alt+Shift+Up/Down scrolls overflowing rows. Tab completes connection names and complete tunnel IDs; the tunnel list command exposes full metadata when a narrow table truncates text. IDs include a per-creation identity and never mean “whatever now occupies this port”. The connection-owned SOCKS proxy remains in the PROXY column, separate from this local-forward inventory.

Verify and remove

Successful allocation means the local listener exists. OpenSSH checks destination reachability and server forwarding permissions when a client uses it. Use the destination service’s normal client against the local endpoint to verify application traffic. tunnel check CONNECTION/ID performs a bounded passive greeting check: it sends no application commands and discards the received byte. It reports observed return traffic, a failure with destination/server guidance, or an inconclusive result for a silent service. It does not promise application authentication or health.

Occupied ports and invalid binds fail without replacing sibling forwards. A lost allocation acknowledgement is reported as unverified with its creation identity; inspect before retrying, and explicitly close the connection if listener cleanup cannot be verified. Removing a selected forward stops new connections to that listener; already accepted streams may finish. Other listeners and the SSH connection remain usable. Keep-running quit retains forwards, while connection close removes all its listeners. Master loss marks its forwards unavailable; reconnect never recreates them.

Ownership and evidence

The retained burrow manager owns the inventory. Creation uses the existing confirmed Hovel throw with immutable endpoints, owner generation and connection creation; Hovel retains the real plan, confirmation and run. Inventory and selected removal use the existing public session-command workaround and bounded SDK diagnostics, with the same audit limitations as connection inspection and close. Raw forwarded traffic and passive check output are not collected artifacts. Existing saved settings and evidence survive removal and connection close.

All capabilities remain in burrow@0.1.0; there is no second daemon or resource registry. Public manager commands are tunnels GENERATION, unforward GENERATION CONNECTION_CREATION ID, and tunnel-check GENERATION CONNECTION_CREATION ID. The forward control is for the confirmed adapter, not a replacement approval route. Retained owners from an earlier binary may lack these controls; close their resources explicitly and restart the manager before reconnecting. Unknown ownership is never adopted.

This follows the pinned LazySSH forward/cancel implementation and its tunnel tests. Intentional differences are explicit bind selection, connection-qualified opaque IDs, immutable review binding, non-secret diagnostics and retained-owner inventory. Same-user manipulation of the master socket outside Burrow is outside that inventory contract. Remote forwarding and general chain consumers remain separate tickets.
