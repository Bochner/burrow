SSH forwarding

Create local or reverse TCP listeners on an existing named connection. Commands work in Burrow management and through burrow --workspace /absolute/workspace COMMAND. Required endpoints come first:

tunnel create gateway forward 8080 localhost 80
tunnel create gateway forward 8080 localhost 80 --yes
tunc gateway l 8080 localhost 80
tunnel create gateway reverse 3000 127.0.0.1 3000
tunc gateway r 3000 127.0.0.1 3000
tunc gateway r 0 127.0.0.1 3000
tunnel list
tunnel check gateway/CREATION_ID
tunnel remove gateway/CREATION_ID
tund gateway/CREATION_ID --yes

In the TUI, the first command opens the existing confirmation recap; Escape or Cancel creates nothing. The CLI returns a review without --yes. To bind approval to that exact review, repeat its --review HASH with --yes. The listening endpoint defaults to 127.0.0.1; select another literal address explicitly, such as 0.0.0.0:8080. Broader binds expose the forwarded service to other hosts. Local forwarding reaches the destination from the SSH server; reverse forwarding reaches it from the local SSH client. IPv6 listening endpoints use brackets, for example [::1]:8080; the separate destination HOST argument uses a bare address, such as ::1. TCP ports must be 1–65535, except reverse LISTEN port 0 requests a random high port.

tunc CONNECTION l LISTEN HOST PORT aliases tunnel create CONNECTION forward LISTEN HOST PORT; r aliases reverse; tund ID aliases tunnel remove ID. Both spellings share validation, immutable review and confirmation. Tab after tunnel create or tunc offers live connection names and directions from the current workspace, excluding saved profiles and closed/lost connections.

The TUNNELS table retains the ID, owning connection, direction, listening endpoint, destination and observed state. Listener and destination cells identify their local or remote side. Alt+Shift+Up/Down scrolls overflowing rows. Tab completes connection names and complete tunnel IDs; tunnel list exposes full metadata when a narrow table truncates text. JSON direction L means local listener and remote destination; R means remote listener and local destination. IDs include a per-creation identity and never mean “whatever now occupies this port”. The connection-owned SOCKS proxy remains in the PROXY column, separate from forwarding inventory.

Reverse listener and local destination

For reverse/r, LISTEN is on the SSH server. HOST PORT is reached from the local SSH client, so 127.0.0.1 names the operator machine, not the server. A missing destination returns required-argument help without creating a listener. Select remote exposure explicitly, for example 0.0.0.0:3000 or [::1]:3000.

Reverse LISTEN 0 (or IP:0) requests a random high port. Burrow tries up to eight candidates in 49152–65535 through actual OpenSSH allocation; it never advertises a merely probed free port. Inventory reports the successfully allocated listen endpoint and preserves requestedListen. Each creation remains independent, including repeated requests to the same destination. This deliberately avoids OpenSSH’s reuse of identical zero-port forwarding requests.

Reverse exposure verification requires a Linux SSH server with readable /proc/net/tcp and, when IPv6 is enabled, /proc/net/tcp6, plus shell access and awk/od. No Python or uploaded helper is required. Burrow checks access before allocation and reads actual listening addresses afterward. Server GatewayPorts overrides that narrow or widen the requested address are refused and the selected listener is cancelled. A broader bind normally needs GatewayPorts clientspecified; GatewayPorts yes can force both wildcard address families and be refused even for an explicit IPv4 wildcard request. Exposure can differ briefly between allocation and verification. This observation trusts the authenticated server’s kernel tables; it is not an independent firewall or Internet-reachability assessment.

Unreadable or malformed observations never count as a verified bind. If cancellation or its verification is uncertain, the creation remains unverified in inventory; inspect it and explicitly close its connection. A remote port already in use is conservatively refused across bind addresses, preserving existing listeners. Same-user changes outside Burrow are outside its ownership contract.

Verify and remove

Successful allocation means the requested local or remote listener exists, not that its destination is reachable. OpenSSH checks destination reachability and server forwarding permissions when a client uses it. Use the destination service’s normal client against the listener on its corresponding side to verify application traffic. tunnel check CONNECTION/ID performs a bounded passive greeting check: it sends no application commands and discards the received byte. It reports observed return traffic, a failure with destination/server guidance, or an inconclusive result for a silent service. It does not promise application authentication or health.

For reverse tunnels, the same check first verifies remote exposure, then opens a channel from the SSH server to the remote listener and waits for a local-destination greeting. It requires server AllowTcpForwarding/PermitOpen access for this diagnostic channel. A server permitting only remote forwarding can still serve normal remote clients even if the diagnostic channel is refused. Use the service’s normal client on the remote host to establish application health; a same-port local service cannot satisfy the reverse check.

Occupied ports and invalid binds fail without replacing sibling forwards. A lost allocation acknowledgement is reported as unverified with its creation identity; inspect before retrying, and explicitly close the connection if listener cleanup cannot be verified. Removing a selected forward stops new connections to that listener; already accepted streams may finish. Other listeners and the SSH connection remain usable. Keep-running quit retains forwards, while connection close removes all its listeners. Master loss marks its forwards unavailable; reconnect never recreates them.

Ownership and evidence

The retained burrow manager owns the inventory. Creation uses the existing confirmed Hovel throw with immutable endpoints, owner generation and connection creation; Hovel retains the real plan, confirmation and run. Inventory and selected removal use the existing public session-command workaround and bounded SDK diagnostics, with the same audit limitations as connection inspection and close. Raw forwarded traffic and passive check output are not collected artifacts. Existing saved settings and evidence survive removal and connection close.

All capabilities remain in burrow@0.1.0; there is no second daemon or resource registry. Public manager commands are tunnels GENERATION, unforward GENERATION CONNECTION_CREATION ID, and tunnel-check GENERATION CONNECTION_CREATION ID. The forward control is for the confirmed adapter, not a replacement approval route. Retained owners from an earlier binary may lack these controls; close their resources explicitly and restart the manager before reconnecting. Unknown ownership is never adopted.

Intentional differences are explicit bind selection, verified reverse exposure, real random allocation, connection-qualified opaque IDs, immutable review binding, non-secret diagnostics and retained-owner inventory.
