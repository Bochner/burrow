Operation logs

Use live following for new work, operation notes for recorded actions, and collected output for saved run evidence. Interactive shell bytes are not recorded.

Watch live activity in another terminal

Current source, unreleased: follow is not in v0.1.0. The operation-note and collected-output viewers below are available in that release.

burrow --workspace /canonical/workspace follow
burrow --workspace /canonical/workspace follow --json

Keep your agent CLI and normal Burrow TUI open, then start follow in a third terminal. It prints new actions, reviews, progress, results and available retained-run stdout/stderr using Burrow’s colors. Output scrolls normally: terminal scrollback, selection, copying and resizing remain available. NO_COLOR or the global --no-color preserves the same text. There is no duration or output-budget requirement. Ctrl+C stops only this observer; commands, connections, transfers, the TUI and other followers keep running.

The selected workspace must already have a verified running Hovel daemon. Following never initializes a workspace, connects to an SSH target, approves a request or collects output. Startup shows current connections, retained runs and transfers, then new evidence. Earlier operation/log history and bytes already captured by existing runs are not replayed. Use logs, run output or collected artifacts for that evidence. Shared interactive shell bytes are outside this feed; issue #96 extends it after production shared sessions arrive.

Disconnects, cursors and JSON

Each viewer keeps its own in-memory Hovel sequence, operation-log file position and run byte offsets. Temporary observation failures print a gap; recovery prints resumed and continues from retained positions. Overwritten Hovel events, a changed daemon, detected operation-log replacement/truncation and vanished observed runs are explicit gaps. A daemon change resets the Hovel cursor to its available new tail. No SSH reconnect or work retry occurs. Restarting the follower starts a new live observation; there is no durable resume token. Operation-log replay after replacement can repeat records. Incomplete, oversized or unsafe operation records retain their position and report an error; the reader processes at most 8 MiB of operation notes per poll.

--json, and stdout redirected to a pipe or file, emits one version-1 JSON observation per line. Every observation includes workspacePath, time, observedAt, source, kind and message. Available correlation fields include id, operation, chain, runID, resourceID, target and sequence; original safe fields remain in details. Output observations carry stream, byte offsets and base64 data, plus capture status. output-end marks the end of a captured stream, including incomplete capture. Offsets are zero when not applicable to that source. See burrow capabilities logs.follow for the field contract. JSON mode never mixes in terminal banners or escape sequences. Startup/argument errors use stderr and a nonzero exit; recoverable source failures are stream observations.

Known credential fields use the operation log’s redaction policy, and terminal controls are escaped. Output bytes remain exact in JSON. Commands, program output and arbitrary message text can themselves contain sensitive customer data: existing commands must not put credentials in arguments or source. Protect redirected feeds like other engagement evidence. The follower creates no audit database or background service.

Browse operation notes

logs or Ctrl+N opens the current workspace’s operation notes in an embedded Vim tab. Use Vim search and navigation normally; mouse-wheel scrolling, Page Up/Down and gg/G are available. Ctrl+N or :q closes the viewer and restores the prior tab, focus and draft. Reopening takes a fresh snapshot. The shortcut is reserved by Burrow in management, file mode and embedded SSH, Hovel and editor tabs; it is not sent to the embedded application. During a confirmation dialog, finish or cancel the dialog first.

The CLI entry is burrow --workspace /canonical/workspace logs, with terminal input. Vim uses Burrow’s private configuration, Catppuccin semantic highlighting and a contrasting timestamp background. NO_COLOR disables syntax colors. Personal Vim configuration and plugins are not loaded. The read-only snapshot is separate from the live log, so even changing Vim options cannot overwrite ongoing records.

Scope and interpretation

Ctrl+L opens a read-only viewer with separate Collected output and Activity log tabs. Tab/Shift+Tab switch tabs, / searches, and Ctrl+L or :qa returns to the previous Burrow screen and draft. Reopening refreshes both snapshots. Like Ctrl+N, Ctrl+L is reserved by Burrow in embedded terminals and waits until an open dialog is dismissed.

Collected output shows retained command and script results registered by run collect or the approved collection in run now, run launch ID --collect and run survey, newest collection first, including closed runs. Each entry gives the command, target, local or remote execution outcome, capture completeness and separate stdout/stderr previews. Each stream preview contains at most 64 KiB with an explicit truncation notice and the full artifact path; it does not reduce the saved output. Control characters are escaped and stream lines are indented. A missing artifact or unavailable activity log is reported in its own view. Hovel's artifact inventory and the original operation log remain authoritative; viewer snapshots do not create another history. Live output uses run follow ID; Markdown reports have their own reports browser.

The owner resolved issue #80 on 2026-09-13: record Burrow-issued operations and shell lifecycle only. Commands and output typed inside interactive SSH shells are not recorded. This is an operation log, not a terminal recorder or a tamper-proof forensic record. Arbitrary tools run inside the Hovel tab are governed by Hovel’s own contracts.

The viewer shows readable, colored summaries of completed operations and failures. Downloads produce one final batch summary with totals, elapsed time and the saved location, including mixed failures or cancellation. Per-file JSON, attempts and implicit discovery remain in the detailed backend log rather than the notes. The viewer is a snapshot; reopen it for later completions.

Detailed backend entries begin with a timestamp with timezone and the operation identity. Workspace, target, correlation ID, status and complete safe structured results follow. Submitted-command records preserve the frontend result, while owner records describe actual work and background completion. A review is not an execution. A saved attempt without a terminal result means the outcome is unknown; inspect the owned resource before retrying. Escaped controls and indented payload lines prevent remote text from creating apparent entry headers. No output is silently truncated by the log writer; existing bounded browsing results retain their incomplete/error labels.

Transfers retain their original get/mget/put identity, every source and actual destination, per-file state, bytes, partial/error details, timing, completion time and aggregate counts. Completion is recorded by the retained owner even after the frontend exits. File contents remain in their files. Working transfers are not automatically registered Hovel evidence.

Storage and failures

Each canonical workspace stores burrow-logs/operations.log in a private 0700 directory with a 0600 file. Descriptor-based path checks reject unsafe ownership, permissions, symlinks and hard links. Cooperating clients serialize appends and snapshots under a filesystem lock and sync writes. Prior entries survive restart; there is no automatic rotation or retention limit.

New operations are refused if their attempt cannot be saved, including connection/profile reviews and mutations. Cleanup and cancellation still run if logging is unavailable and report the audit failure. Completion-write failure is returned or retained in connection/download status. Retained shells expose asynchronous completion-log failures in auditError; selected cleanup still runs and reports failures. A partial record prevents further appends and viewing from claiming a complete snapshot. Preserve the original file and investigate storage before manual repair. No automatic recovery deletes evidence.

Authentication answers, private-key contents and secret-bearing structured fields are excluded. Connection output uses existing safe results and classified authentication errors. This does not guarantee that arbitrary remote output or customer filenames contain no sensitive information; protect these logs as engagement records.

LazySSH’s pinned logging_module.py and logging tests preserve command identity, transfer paths, sizes and success/failure. Burrow intentionally replaces its debug-only/truncated command output and transient per-connection log location with complete safe workspace records and durable transfer totals; it does not reproduce LazySSH’s additive/reset counter behavior.
