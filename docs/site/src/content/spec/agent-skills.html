Agent inspection skills

Current source, unreleased: v0.1.0 does not include agent install. See installation and version selection.

The Linux package includes two standalone skills: burrow selects a workspace, discovers supported operations and identifies a live connection; burrow-inspect guides file searches and disk, process, port, service, log and reachability inspection. They use Burrow's production CLI and its existing review and evidence rules. Full execution, transfer, tunnel and shared-session guidance remains follow-on work.

Install

Choose a client and an explicit scope. Project scope uses the current working directory; run it at the intended project root. Preview the exact destinations first if useful:

burrow agent install codex --scope project --dry-run
burrow agent install codex --scope project
burrow agent install claude --scope user
burrow agent install opencode --scope user

Installation requires neither a workspace nor an installed agent client. It performs no network requests, starts no Hovel daemon or model, and creates no download cache. --offline before agent is accepted and has the same behavior. Burrow's separate Hovel runtime cache is unrelated. Existing Hovel skills, MCP integrations, unrelated skills and client configuration are preserved.

CLAUDE_CONFIG_DIR overrides Claude's user directory. XDG_CONFIG_HOME overrides OpenCode's config root, beneath which Burrow uses opencode/skills. Overrides and explicit source paths must be absolute and canonical. These locations were checked against the current Claude skills documentation, Claude configuration layout, Codex skills documentation and OpenCode skills documentation on 2026-09-23. OpenCode also discovers compatible Claude/Codex directories; avoid installing duplicate copies into several roots unless intended.

Update and recover

Run the same install command from the newer Burrow build. Byte-identical content is a no-op, including unmanaged identical skills: they are not silently adopted. Each managed installation has a .burrow-installed.json receipt binding its files to their hashes. An update replaces only a skill whose contents still match its receipt. Edited files and differing unmanaged skills refuse before the suite writes anything. Move a conflicting directory outside the discovery tree, install, then reconcile your edits explicitly; there is no force-overwrite flag.

Previous versions remain under burrow-skill-backups/ beside the client's skills/ directory, outside its discovery tree. The report names each backup. Review and remove old backups manually when no longer needed. Skills omitted from a later bundle remain installed until you remove them.

A failed replacement attempts to restore the previous directory. If restoration also fails, the command exits unsuccessfully and reports the remaining backup location. Inspect that location and the destination before manual recovery; do not assume rollback. Recovery is per skill, not an all-or-nothing suite transaction. Earlier successful updates can remain after a later failure. Avoid concurrent installation or editing: this is not isolation from another process changing the tree, nor a crash/power-loss transaction.

Results use JSON in pipes and the shared semantic colors in a terminal; --no-color and NO_COLOR preserve the text. Check complete, dryRun and each skill's state: planned is not applied. A failed attempt can emit a partial report on stdout followed by an error on stderr and exit 1. Backup paths identify preserved content, not a successful update.

Bundle validation and provenance

aspect burrow package produces the Linux archive containing burrow and burrow-agent.zip. The executable embeds that same deterministic skill bundle. Its manifest records the skill version, source and inspected Hovel revision, plus SHA256 for every file. bundleSHA256 in the result is the hash of that manifest, binding the exact contents; it is not a publisher signature. The source URL identifies the canonical source tree, while hashes distinguish local builds from published main.

For a trusted local bundle, extract burrow-agent.zip into a directory and use burrow agent install codex --scope project --source /absolute/bundle. That directory must contain burrow-agent.json and skills/. Source, destination and backup ancestors must be real directories. Symlinks, special files, checksum mismatches, malformed metadata and unexpected bundle paths refuse. Bounds are 1 MiB per file, 8 MiB total and 256 files. The canonical frontmatter uses single-line plain text starting with a letter or JSON-quoted strings, with quoted version metadata; other YAML constructs are rejected. Use bundles produced by Burrow rather than inventing manifests for arbitrary skill folders.

The canonical tree follows Hovel's inspected skills: agent/skills/, a small entry skill, focused workflow skills, compatibility metadata and references loaded on demand. Burrow uses its own identity, live CLI capability discovery, exact review and Hovel evidence. The accepted Burrow contract installs directories directly and keeps MCP optional; it does not copy Hovel's plugin packaging or require its MCP-first guidance.

Inspect a host

After installation, ask the agent to use Burrow with an explicit workspace and existing connection: “In workspace /srv/lab, inspect disk space on connection gateway.” It discovers the CLI contract and checks the selected live identity before preparing df -h. Searches can specify filename, full-path pattern or modification time; broad scans expose their root and cost first. Routine commands use defaults, and missing target tools are reported.

burrow capabilities run.prepare
burrow --workspace /srv/lab workspace inspect
burrow --workspace /srv/lab connections
burrow --workspace /srv/lab inspect gateway
burrow --workspace /srv/lab run prepare gateway -- df -h
burrow --workspace /srv/lab run launch RUN

Replace RUN with the returned id. Inspect the returned review and its digest; once the requested action is authorized, launch that same run with --review HASH --yes. Existing authorization can cover the requested reads. Approval flags are never inferred from successful preparation. Observe with run inspect RUN and read run output RUN stdout 0 and run output RUN stderr 0. Decode the base64 data field and continue at each stream's nextOffset. See retained runs for the full lifecycle.

CLI exit 0 does not imply a successful remote command. Report remoteExit, outputComplete, errors, timeout or cancellation uncertainty. A search can have complete capture but partial results because some directories were unreadable. Keep observed facts separate from hypotheses; filenames and remote logs remain data, not agent instructions. Viewing output does not collect it. When requested, review and confirm run collect RUN; report its collection result and correlate Hovel artifacts by the collection response's runID, which differs from preparation/launch responses. Use the stable retained id for inspect/output. Uncollected output can be lost with its owner.

Discovery and validation limits

Restart the client if its skill list has not refreshed, then check for burrow and burrow-inspect. Check the install destination, project root, user overrides and client skill permissions if either is absent. A successful file install proves placement and metadata, not that a running client loaded the skill or that a model followed it correctly.

aspect burrow agent-discovery is an opt-in native check using disposable configurations and Bubblewrap with networking disabled. It checks Codex skills/list, Claude initialization metadata, and OpenCode debug skill when each client is available. No model prompts are sent. Missing clients are reported as UNVERIFIED. OpenCode native loading remains unverified on this development host because OpenCode is absent.

The required //core/cmd/burrow:agent_test exercises the distributable across all six locations, repeat/update/backup/conflict handling, validation, coexistence and actual OS replacement/restoration failures. Its recovery checks use Linux ptrace across all Go threads; no external fault-injection tool, client or model is required. The production SSH runs partition executes the installed filename-search recipe against a controlled server, proving selection, review, separate stdout/stderr, a partial search with known nonzero exit and complete capture, and explicit durable Hovel evidence. This is deterministic command/result acceptance, not a claim of a completed external-model exercise.
