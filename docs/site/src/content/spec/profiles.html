Saved connection collections

A profile is a saved recipe for connecting, such as “NAS”. A collection is a JSON file containing those recipes, such as “Homelab”. Opening a collection displays saved settings only: it never authenticates, resolves SSH aliases, opens a shell or creates tunnels. Choose a profile and explicitly connect when ready.

Automatic template

Opening a verified workspace with status, tui or workspace open (v0.2.0) automatically creates WORKSPACE/burrow-profiles.json if it is missing. Existing bytes are never replaced during startup. The file is private (owner read/write, mode 0600), outside the disposable connection directories. This is also the default collection until another is selected.

burrow --workspace /home/alice/lab status
# Template: /home/alice/lab/burrow-profiles.json
burrow --workspace /home/alice/lab profiles

JSON has no comment syntax. The template uses _comment for instructions and _example for an inactive example. The sample is never listed as a saved connection. Copy it into profiles and edit the settings, or let Burrow save profiles for you.

{
  "version": 1,
  "_comment": "Copy _example into profiles and edit it. Never store passwords or private keys.",
  "_example": {
    "name": "example",
    "host": "192.0.2.10",
    "user": "alice",
    "port": 22
  },
  "profiles": []
}

The generated instructions also name the create/save commands. _comment and _example are optional documentation fields; Burrow preserves them when editing and backing up the collection. Put only connection settings and explanatory text in this file, including its documentation fields.

A filled-out collection

Here is a complete example with an explicit NAS endpoint and an SSH alias for a build server. Replace the example addresses, usernames and paths with your own. Profile names use 1–24 ASCII letters, digits, underscores or hyphens, starting with a letter or digit.

{
  "version": 1,
  "profiles": [
    {
      "name": "nas",
      "host": "192.168.1.20",
      "user": "alice",
      "port": 22,
      "key": "/home/alice/.ssh/id_ed25519"
    },
    {
      "name": "build",
      "host": "build-alias",
      "user": "-",
      "port": 0,
      "sshConfig": "/home/alice/.ssh/config",
      "jump": "alice@bastion.example:22"
    }
  ]
}
FieldMeaning and example
nameProfile name, also the default live connection name: nas.
hostHostname, IP address or trusted SSH alias: build-alias. Aliases are kept as aliases when saved.
userExplicit username, or - to use SSH configuration.
portExplicit port 1–65535, or 0/omitted to use SSH configuration or 22.
passwordAuthOptional boolean, saved by --password. Selects password-only authentication with hidden entry when connecting; stores no password. Cannot be combined with a key or fixed nonempty agent.
keyOptional absolute key-file reference. The key bytes are never copied.
sshConfigOptional absolute trusted SSH config path. Omitted uses the current user's default.
jumpOptional explicit jump chain, such as alice@bastion.example:22; omitted inherits configuration.
proxyPortOptional SOCKS listener port (1–65535), explicitly bound to 127.0.0.1. Omitted or zero means off; separate from jump hosts.
agentExplicit, agentNormally omit both: resolve the current frontend agent/config at connect time. For a deliberately fixed agent, use "agentExplicit": true, "agent": "/run/user/1000/agent.sock". To disable agent use, set agentExplicit true and agent to an empty string.

Key, agent and SSH-config paths must be absolute and canonical when supplied. File copies between computers may need path edits. Burrow validates the schema and names on load, but does not open key files or evaluate SSH configuration. A saved row may show “Config” or “Config/agent” until explicit connect resolves it. Match exec can execute local commands during SSH configuration evaluation: choose trusted configuration and review the resulting endpoint.

Create, inspect and connect

burrow --workspace /home/alice/lab profile create nas 192.168.1.20 alice --key /home/alice/.ssh/id_ed25519
burrow --workspace /home/alice/lab profiles
burrow --workspace /home/alice/lab profile select nas
burrow --workspace /home/alice/lab profile connect nas --prompt
# A second live instance can have a different name:
burrow --workspace /home/alice/lab profile connect nas --as nas-maintenance --prompt

Create saves without authenticating. Select displays settings without connecting. Connect uses the shared reviewed SSH flow. For unattended key/agent use, profile connect nas --yes launches an asynchronous retained attempt; inspect its state with inspect nas. --prompt waits for authentication with private terminal entry. The TUI always uses its embedded authentication flow.

Save an active connection for later

burrow --workspace /home/alice/lab connect nas 192.168.1.20 alice --prompt
# After successful authentication, Burrow offers “Save profile as”.
# Enter accepts the name; edit it to choose another; Escape skips saving.

# Save manually, including a connection retained from an earlier frontend:
burrow --workspace /home/alice/lab profile save nas
burrow --workspace /home/alice/lab profile save nas --as home-nas

# Later, after explicitly closing the old live connection:
burrow --workspace /home/alice/lab close nas --yes
burrow --workspace /home/alice/lab profile connect home-nas --prompt

Only an authenticated active owner can supply reusable settings. A failed, connecting or lost connection cannot be saved as a successful connection. Saving preserves original alias/override choices, not the resolved address or an inherited temporary agent socket. Unchanged profiles do not trigger another automatic save offer. The offer uses the active connection's name by default; an existing different profile requires replacement review. Skipping or failing a save leaves the successful connection alive. A noninteractive asynchronous connection offers no terminal dialog: use profile save after observing connected.

Profiles contain no passwords, passphrases, private-key contents, process IDs, master sockets, authentication-helper sockets or one-time trust approvals. They are settings, not a credential backup. The knownHosts setting was removed in issue #73. Remove it from older collections before loading them; existing files and known-host records are not rewritten or deleted. Do not put secrets in command arguments, collection comments or example fields.

Edit and delete

# Edit replaces the full saved recipe; include options you want to keep.
burrow --workspace /home/alice/lab profile edit nas 192.168.1.21 alice --port 2222 --key /home/alice/.ssh/id_ed25519
# Read the review, then repeat with --yes to approve.
burrow --workspace /home/alice/lab profile edit nas 192.168.1.21 alice --port 2222 --key /home/alice/.ssh/id_ed25519 --yes
burrow --workspace /home/alice/lab profile delete nas
burrow --workspace /home/alice/lab profile delete nas --yes

Changing or deleting the recipe affects future connections only. An already connected NAS remains connected, and its evidence remains. Use close NAME to end a live resource. The TUI's Edit action fills the complete command with current settings. Review responses include the collection path and revision; automated callers can repeat those as --collection PATH --revision HASH --yes to refuse changes since review. The TUI carries these values automatically. A stale edit must be reviewed again.

Open another collection and make backups

# Create/open a collection in an existing trusted directory:
burrow --workspace /home/alice/lab profile collection /home/alice/homelab.json
# Every later save/edit/delete uses that selected file, even in another invocation.
burrow --workspace /home/alice/lab profile create router 192.168.1.1 admin

# Open an existing file, never connect automatically:
burrow --workspace /home/alice/lab profile load /home/alice/homelab.json
burrow --workspace /home/alice/lab --load /home/alice/homelab.json tui

# Backup destination must be new; existing backups are preserved.
burrow --workspace /home/alice/lab profile backup /home/alice/homelab-before-changes.json
# To use that backup, explicitly open it:
burrow --workspace /home/alice/lab profile load /home/alice/homelab-before-changes.json
# To return to the workspace default:
burrow --workspace /home/alice/lab profile load /home/alice/lab/burrow-profiles.json

This is an open-and-edit model. Loading a backup makes the backup itself the selected editable collection. Two workspaces opening the same file share future profile edits; they still own separate live connections and evidence. Hovel remembers the selected file path per workspace. Backing up Hovel alone does not copy an external collection; use the profile backup command or include the file in your own backups.

Invalid JSON, unknown fields, duplicate profile names, unsupported versions, unsafe paths/permissions and missing selected collections produce visible errors. Failed loads keep the previous selection. Saves use private temporary files and atomic replacement; failures preserve prior data, and conflicting edits are refused. Collections are bounded to 1 MiB. Symlink collection paths and untrusted writable parent directories are refused. An error after replacement but before filesystem synchronization reports uncertain durability rather than claiming the old bytes remain. There is no automatic overwrite of backups, legacy LazySSH import, cloud synchronization or automatic reconnect.

Terminal actions

The saved table uses the shared Catppuccin field colors and remains separate from active SSH connections. Focus Saved with F6/Shift+F6, choose a row with arrows, and press Enter for actions; clicking the section title also opens actions. Clicking a row selects it without connecting. Actions populate the shared command prompt so you can finish or review the command before submitting. Tab completes profile names, editable settings, active connection names and connection options. F1 opens help. Narrow and no-color layouts retain keyboard access. Proxy shows the saved SOCKS port, or a dash when off; it never means a jump host. No-Term is Yes because masters are shell-free. Interactive shells are opened separately and do not change the saved recipe.

Hovel profile automation and retained history 
# Retained profile management history:
burrow --workspace /home/alice/lab history

# Through the existing burrow@0.1.0 Hovel module in a chosen chain:
chain config set workspace /home/alice/lab
chain config set command "profile create nas 192.168.1.20 alice"
throw --now --allow-dangerous

The module's optional command input accepts saved-profile management commands and returns structured results. It must run under the verified workspace daemon. profile connect uses Burrow's reviewed retained-manager connection path and private frontend prompts; it is not accepted through the module's command input. The old connection JSON input is also retired and refused. For connection automation, generate a saved connection chain. Hovel’s danger allowance is module-wide, so workspace/profile throws also require --allow-dangerous; profile edit/delete review checks still apply. Keep explicit operation/chain selection when automating Hovel. Management history uses Hovel's retained logs and timestamps; authentication answers and invalid commands from the Burrow command seam are excluded. History follows Hovel's existing retention policy, not an unlimited transcript. Module stdout remains framed JSON-RPC.

Validation 
aspect test //core/cmd/burrow:profile_test
aspect test //core/cmd/burrow:interaction_test
aspect burrow ssh-check
aspect burrow-site check
aspect burrow-check ci
aspect burrow-check

The portable profile check runs actual Burrow commands against an isolated Hovel workspace: template creation, load-only behavior, collection selection across invocations, backup/reopen, invalid/unwritable inputs, conflicts, persistent history and SDK commands. It watches a listener and an executable SSH-config marker to catch accidental network/config evaluation. The controlled SSH check covers saving an authenticated owner, profile-to-connect, edit/delete preserving live resources, and interactive save-after-success with secret canaries. Terminal checks cover the saved table, actions, completion, colors, narrow layouts and save dialog.

Source evidence: issue #47, the accepted ownership/load-only policy, and pinned LazySSH configuration source. Unlike LazySSH's default-path save helpers and single overwritten backup, every operation uses the selected source and backups refuse existing destinations. Human approval of visual polish remains distinct from automated acceptance.
