Quit, detach and close

A connection is an authenticated SSH transport. A shell is one terminal using it. Leaving a view, ending a shell and closing its connection have different effects.

A disappeared frontend leaves its claim until takeover; labels do not assert liveness. This replaces v0.1.0’s frontend-local shell lifetime.

Leave and return

  1. Use connections, transfers and run list to inspect work in the selected workspace. Collect important completed run output before leaving.
  2. Enter quit in management. Review the connections across all workspaces you opened. Keep running retains the daemon-owned resources; Close connections ends the reviewed connections.
  3. Reopen Burrow with the same absolute workspace path. Inspect the retained resources. Select a discovered retained shell to observe it, then explicitly take control with Alt+T if needed.

Failed or uncertain teardown keeps Burrow open with an error. Inspect that result before retrying. Ending a local SSH client never proves that deliberately detached remote processes have stopped.

Close one connection from the CLI

burrow --workspace /absolute/workspace inspect gateway
burrow --workspace /absolute/workspace close gateway
# v0.2.0: copy the digest from the review after approving it.
burrow --workspace /absolute/workspace close gateway --yes --review HASH

v0.2.0 binds the review to the exact connection creation and observed state. Changed state requires another review. --yes without a digest explicitly approves the current selection; v0.1.0 supports that older form. Connection names can be reused later, so never treat a name or port as a permanent identity.

Manager retirement and loss

The v0.2.0 workspace restart and workspace retire commands review the entire connection owner, including connections added concurrently. They preserve the daemon and separate retained-run records, but ending their SSH masters loses access for remote runs. Restart also registers the current executable. Neither reconnects SSH or starts a replacement manager. See the headless lifecycle workflow.

After owner or daemon loss, saved profiles and already collected artifacts remain. Live state may be lost or unverified, uncollected output may be unavailable, and remote process cleanup may be unknown. There is no automatic login, shell recovery or adoption of stale sockets. Follow ownership recovery guidance.
