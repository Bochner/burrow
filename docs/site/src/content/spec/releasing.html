Release preparation

Burrow follows Hovel's prebuilt Go wheel and PyPI Trusted Publishing approach. The local release path is prepared; no public PyPI release is claimed. The distribution name is burrow-ssh and its console command is burrow. The public PyPI name burrow belongs to another project.

Build and verify locally

aspect burrow-check preflight
aspect burrow-release bundle

The bundle contains the archive, exact smoke-tested wheel, SHA256SUMS and bundle.json. Use a fresh dist/ directory; preserve earlier artifacts elsewhere before rebuilding. The wheel lands under dist/, with its version taken from root VERSION. The declared release binary is Linux amd64 without CGO; the wheel targets manylinux_2_28_x86_64, matching the managed Hovel runtime's Linux floor. No Go compiler or separate Hovel installation is needed on the operator host. The Python 3.10+ launcher replaces itself with the Go executable, preserving arguments, streams, signals and exit status.

The required portable gate includes offline installation through digest-pinned pipx, deterministic wheel/RECORD checks, CLI error propagation, embedded skill installation, pinned Hovel startup, and upgrade/uninstall state preservation. The application keeps its embedded skill bundle and canonical base-module manifest. Packaging does not replace live workspace managers; the usual explicit restart and reconnect rules apply.

GitHub release

The public v0.2.1 GitHub release distributes the Linux amd64 archive, wheel and SHA256SUMS. For subsequent releases, successful main CI prepares the complete distribution and smoke-tests the exact files through offline pipx install/upgrade/uninstall, CLI, embedded skills and pinned Hovel checks. The archive is extracted and checked too. The Release workflow automatically promotes this bundle when VERSION increases, without another full gate or package build; GitHub publication does not depend on PyPI setup.

Click Add. This creates a pending publisher, not a release or name reservation. No API key or copied LazySSH secret is required. The GitHub environment pypi is prepared with protected-branch deployments; the workflow additionally restricts publishing to dispatches from main. Its publishing job uses a short-lived OIDC credential. See PyPI's pending-publisher instructions. The chosen name was unregistered when checked; PyPI must still accept it at first publication.

Automatic version releases

Each PR must increment root VERSION above main and add a matching nonempty ## [VERSION] section to CHANGELOG.md. Bump once per PR and keep its notes current. Use X.Y.Z for stable versions or X.Y.Z.devN for development prereleases. Patch versions cover fixes and tooling, minor versions compatible features, and major versions breaking changes. Recheck the version after updating from main.

After the owner requests the PR and merge, successful main Repository CI automatically starts Release. It compares VERSION with the previous main revision, creates vVERSION at the tested commit, and publishes the exact bundle with the matching changelog notes. An unchanged version skips publication. Downgrades, missing notes and existing tags pointing elsewhere fail; tags are never moved. Development versions are marked as prereleases. Rerunning the workflow can complete the same release without replacing existing assets.

Publication validates main membership, successful source CI run/attempt, artifact digest, exact file set and distribution checksums. Both validation and publishing use the immutable tested commit. Automatic publication takes its bundle from the triggering Repository run; it never substitutes another revision or reruns the application gate. PyPI stays manual.

Manual rehearsal and optional PyPI publication

Run Release from main with destination rehearsal to verify a successful main bundle without publishing. A tag is optional for rehearsal; a supplied tag must match VERSION and the checked-out commit. For an existing version tag, destination github can complete GitHub publication, or github-and-pypi can also publish its verified wheel after the one-time PyPI setup. Stable releases default to normal release status; the manual prerelease option can opt in. Development versions remain prereleases.

Bundles expire after 30 days. If no verified bundle exists, Release fails clearly; dispatch Repository with force_full if that revision is still main HEAD, then retry. Automatic reconstruction of older revisions is unsupported; prepare a new release revision on main instead. Do not substitute another revision’s bundle. Pushing a tag alone does not publish.

The optional PyPI job alone receives id-token: write. It publishes only the verified wheel through the pinned PyPA action with attestations and checks PyPI's filename/digest afterward. An existing same-version file with a different digest fails. GitHub publication proceeds independently, so a PyPI failure can leave a successful GitHub release; inspect both job results before retrying. Both the GitHub repository and its release downloads are public.

The required preflight includes all Hovel compatibility checks; the temporary #86 exception is retired with v0.4.4. The owner waived the manual walkthrough and accepted v0.2.0 in #65; later versions publish automatically after an owner-authorized merge and successful CI. Hovel source attribution and release-tool changes are recorded in core/tools/release/UPSTREAM.md.
