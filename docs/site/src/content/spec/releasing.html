Release preparation

Burrow follows Hovel's prebuilt Go wheel and PyPI Trusted Publishing approach. The local release path is prepared; no public PyPI release is claimed. The distribution name is burrow-ssh and its console command is burrow. The public PyPI name burrow belongs to another project.

Build and verify locally

aspect burrow-release build
aspect burrow-release check
aspect burrow-check preflight

The wheel lands under dist/, with its version taken from root VERSION. The initial candidate is 0.2.1.dev0. The declared release binary is Linux amd64 without CGO; the wheel targets manylinux_2_28_x86_64, matching the managed Hovel runtime's Linux floor. No Go compiler or separate Hovel installation is needed on the operator host. The Python 3.10+ launcher replaces itself with the Go executable, preserving arguments, streams, signals and exit status.

The required portable gate includes offline installation through digest-pinned pipx, deterministic wheel/RECORD checks, CLI error propagation, embedded skill installation, pinned Hovel startup, and upgrade/uninstall state preservation. The application keeps its embedded skill bundle and canonical base-module manifest. Packaging does not replace live workspace managers; the usual explicit restart and reconnect rules apply.

One-time PyPI setup

Sign into PyPI Account → Publishing and add a pending GitHub publisher with these values:

FieldValue
PyPI project nameburrow-ssh
OwnerBochner
Repositoryburrow
Workflow filenamerelease.yml
Environmentpypi

Click Add. This creates a pending publisher, not a release or name reservation. No API key or copied LazySSH secret is required. The GitHub environment pypi is prepared with protected-branch deployments; the workflow additionally restricts publishing to dispatches from main. Its publishing job uses a short-lived OIDC credential. See PyPI's pending-publisher instructions. The chosen name was unregistered when checked; PyPI must still accept it at first publication.

Rehearse, then publish an approved tag

After the owner requests merging the preparation, use GitHub Actions → Release → Run workflow on main. Leave Publish disabled for a build-only rehearsal. A tag is optional for rehearsals; supplied tags must match VERSION and the checked-out commit. The workflow runs the full required preflight, builds and checks the wheel, and uploads the artifact without contacting PyPI for publication.

For an owner-authorized release, commit the intended VERSION (X.Y.Z or X.Y.Z.devN), merge through the normal approved PR path, and create the matching vVERSION tag. Run Release from main with that existing tag and Publish enabled. Publication requires a clean tagged commit contained in main and passing verification/build jobs. The build and publishing jobs check out the verified immutable commit, not a tag resolved again later.

Only the separate publishing job receives id-token: write. It uploads the tested wheel through the pinned PyPA action with attestations, verifies the PyPI filename's SHA256 against the local artifact, and then attaches that wheel to the GitHub development release. An existing same-version file with a different digest fails verification. All uploads remain explicit; pushing a tag alone does not publish. Public PyPI uploads are publicly downloadable even though this GitHub repository is private.

The required preflight includes all Hovel compatibility checks; the temporary #86 exception is retired with v0.4.4. The owner waived the manual walkthrough and accepted v0.2.0 in #65; each later release still requires its own verification and publication approval. Hovel source attribution and release-tool changes are recorded in core/tools/release/UPSTREAM.md.
