Launch a workspace

The initial production capability is verified setup on Linux amd64 (issue #44). It opens the Catppuccin management interface in an explicitly selected Hovel workspace. The named SSH connection flow adds real retained OpenSSH masters, and saved connection collections preserve settings for future sessions with an automatic JSON template. Tunnels, shells, transfers and runs remain subsequent tickets; unavailable capabilities are labelled and contain no fixture resources.

Build and run

aspect burrow package
aspect burrow run -- --workspace /absolute/private/workspace
aspect burrow run -- --workspace /absolute/private/workspace --offline status
aspect burrow check

The declared //core/cmd/burrow:package target produces a Linux package containing the burrow Go executable and a public-SDK module manifest. Extract the archive into an operator-owned directory and run burrow --workspace /absolute/private/workspace. A real input/output terminal is required for the TUI; status prints verified identity as JSON. Arguments before the command may be reordered. --help performs no setup.

Dependency and identity

First launch downloads the exact Hovel v0.4.2 Linux amd64 wheel selected in the setup proof. Alternatively, supply that wheel with --hovel-package FILE. The package cache is $XDG_CACHE_HOME/burrow/hovel/0.4.2, or ~/.cache/burrow/hovel/0.4.2. A verified cached executable works offline. There is no executable-path or checksum override.

The wheel SHA-256 is 7edccdabe04e30098e417d27ab48064c11a8612149124b7df0797251e88a0933; its fixed hovel/bin/hovel member has SHA-256 a7bcd5f2fa885244d160b722a6ffbd28f3bbae9777b9d510119a203d08788cc1. The SDK/source pin is c461ba282a8aecc7aa3a079a4613bf5e2640c388, as recorded in MODULE.bazel. Existing Charm v2 pins and the accepted prototype's Dracula palette/layout are reused without dependency upgrades.

For canonical workspace W, the receipt is W/burrow-launch.json, the private connection runtime root is W/burrow, and Hovel retains its W/hoveld.sock, daemon.json and daemon.lock conventions. Startup serializes on the workspace directory. Reuse verifies the independent executable digest, Linux boot/start identity, a pidfd, actual Unix socket peer, public daemon identity and recorded directory/socket identities. The receipt cannot select another workspace. Each status request reconnects only after performing verification; it never retries an operation on an unverified replacement connection.

Refusal and recovery

Runtime/cache directories are owner-only 0700 and receipts are bounded regular 0600 files. Containing paths must be safe from replacement by other users and contain no symlinks. Existing unsafe permissions are refused without changing them. A root-owned sticky temporary directory is permitted as an ancestor of a private test workspace.

Invalid downloads cannot publish an executable. Interrupted publication leaves a visible .pending reservation that subsequent launch refuses. An unknown runtime root, socket, daemon lock/status or incomplete receipt cannot be legitimized by a new daemon. A too-long endpoint requires an explicitly chosen shorter workspace path; no alternate root is selected.

On refusal, investigate the exact reported path, its ownership and the associated process/socket identity before manually recovering it. Inability to connect alone does not establish that deletion is safe. There is no force-delete, automatic restart or adoption path. Startup diagnostics are retained in private W/burrow-launch.log; failed-launch evidence and existing workspace files are preserved. Normal quit leaves the daemon running. After daemon loss, a later launch refuses the stale receipt.

Interface and checks

In the TUI, status revalidates the selected workspace, help or F1 opens the command reference, and quit opens a confirmation. Tab accepts a selected completion. Help preserves the draft. NO_COLOR and --no-color provide plain presentation; there are no progress animations. Remote/control text is escaped before display.

The packaged burrow module entry point serves only public SDK framed JSON-RPC. The single public identity is burrow@0.1.0. It requires an explicit workspace input: no action input inspects the workspace, command manages saved profiles, and connection creates a retained SSH owner. Command and connection inputs are mutually exclusive, and connection JSON must name the same workspace. Verification never bootstraps another daemon. Every Hovel throw requires --allow-dangerous because the SSH-capable module retains its danger tag. SDK logging stays on the protocol channel.

aspect burrow check exercises the packaged frontend against real disposable Hovel daemons, concurrent and offline launch, unsafe/stale/replaced resources, refusal without mutation, public SDK framing, controlling-PTY input and VT-rendered state, terminal restoration, evidence preservation and daemon loss. It is included in both portable and full Burrow gates. These setup checks do not claim SSH parity; controlled SSH checks remain part of the full gate.
