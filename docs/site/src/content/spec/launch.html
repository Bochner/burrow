Install and launch

Burrow supports Linux amd64. It installs a verified Hovel runtime on first workspace launch and manages that local daemon. You do not need to install Hovel separately or run it on the SSH target.

On this page: Available distribution · Requirements · Build and install · Open your first workspace · Offline and managed Hovel setup · Upgrade deliberately

Available distribution

The v0.2.1 release provides burrow-v0.2.1-linux-amd64.tar.gz, a pipx wheel and SHA256SUMS. Download the public archive and checksums, then verify before extracting:

sha256sum --check --ignore-missing SHA256SUMS
mkdir -m 700 "$HOME/burrow-v0.2.1"
tar -xzf burrow-v0.2.1-linux-amd64.tar.gz -C "$HOME/burrow-v0.2.1"
"$HOME/burrow-v0.2.1/burrow" --help
export PATH="$HOME/burrow-v0.2.1:$PATH"

Use a fresh operator-owned directory. Release notes identify the exact source commit and archive digest. The archive contains burrow, hovel-module.yaml, burrow-agent.zip and Hovel's license; it downloads the separately pinned Hovel runtime on first launch. There is no automatic updater.

The older v0.1.0 release has source only and lacks capabilities, workspace subcommands, follow and agent install. The public module identity burrow@0.1.0 is not a feature-version check. See release scope and acceptance status.

Build and install

For the released baseline, clone the public release tag:

git clone --branch v0.2.1 https://github.com/Bochner/burrow.git
cd burrow
aspect burrow package

For a current-source build, run aspect burrow package in that checkout instead. Record git rev-parse HEAD and any local changes with your build. The declared output is bazel-bin/core/cmd/burrow/package.tgz. Extract it into a new operator-owned directory:

mkdir -m 700 "$HOME/burrow-install"
tar -xzf bazel-bin/core/cmd/burrow/package.tgz -C "$HOME/burrow-install"
"$HOME/burrow-install/burrow" --help
export PATH="$HOME/burrow-install:$PATH"

Choose another fresh directory if that destination already exists. The PATH change applies to this shell; use the absolute executable path or add that directory to your shell configuration for later sessions. The package contains the executable, hovel-module.yaml, Hovel's license and burrow-agent.zip, whose contents are embedded in the executable.

Open your first workspace

Install the release wheel with pipx

Download the wheel and SHA256SUMS from the GitHub release, verify them as above, then install the local file. The wheel has not been published to PyPI. You can also build it from the release checkout with aspect burrow-release build; that output lands under dist/.

pipx install ./burrow_ssh-0.2.1-py3-none-manylinux_2_28_x86_64.whl
burrow --help

This requires pipx and Python 3.10 or later, plus the Linux/OpenSSH requirements above. The package contains the Go application; Python only launches it. Burrow still installs and verifies its own pinned Hovel. The distribution is burrow-ssh; pipx install burrow refers to an unrelated project. For a newer local wheel use pipx install --force /absolute/new-wheel.whl. Once public releases exist, use pipx upgrade burrow-ssh. Uninstall with pipx uninstall burrow-ssh; workspace state, installed agent skills, retained processes and the Hovel cache remain. Review and close live resources deliberately before removing the frontend. See release preparation.

burrow --workspace "$HOME/burrow-lab"

The default command opens the Catppuccin Mocha management interface. Use a short absolute canonical path under a trusted parent; Burrow creates absent private workspace directories. Symlinks, unsafe permissions and overly long socket paths are refused. A workspace separates settings and evidence, but does not isolate processes running as the same user.

In management, enter connect for guided entry. Use help or F1 for commands and Ctrl+P for the searchable menu. Follow connections and workspace navigation next.

For JSON setup without a TUI, use the release-compatible status command:

burrow --workspace "$HOME/burrow-lab" status

status initializes or reuses a workspace; it is not a read-only probe of an absent workspace. Use workspace open for the same operation and workspace inspect to verify an existing daemon without initializing it. Each invocation needs its own explicit workspace. Global flags such as --offline and --no-color go before the command.

Offline and managed Hovel setup

Normal first launch downloads the exact Hovel v0.4.4 wheel and extracts its verified executable; it does not run pip. Later launches reuse the verified cache at $XDG_CACHE_HOME/burrow/hovel/0.4.4, falling back to ~/.cache/burrow/hovel/0.4.4. XDG_CACHE_HOME, when set, must be absolute.

# An already populated, verified cache:
burrow --workspace "$HOME/burrow-lab" --offline status
# First launch using an existing copy of the exact pinned wheel:
burrow --workspace "$HOME/burrow-lab" --offline --hovel-package /absolute/hovel-0.4.4-py3-none-manylinux_2_28_x86_64.whl status

Obtain that exact wheel from Hovel v0.4.4. These options are for offline environments; they are not required normal setup. A different wheel or executable is refused. Burrow supports its own pinned local daemon, not adoption of an arbitrary existing Hovel installation or remote daemon.

The independent archive and executable digests are enforced by core/launch/package.go. The package cannot override them. Burrow's module manifest uses its public SDK; protocol stdout is framed JSON-RPC, while the frontend owns terminal presentation.

Upgrade deliberately

  1. Build the intended source revision and extract into a fresh directory. Keep the old executable while its retained resources still need it.
  2. Before a Hovel runtime upgrade, use the old Burrow executable to inspect and close active connections and retained work. Then gracefully stop that workspace’s old Hovel daemon and wait for it to exit. The new executable refuses a running daemon whose executable differs from its pin; it never replaces it automatically.
  3. Open the same workspace with the new executable to start the pinned runtime and register the base module. Preserve the workspace directory, saved settings and collected evidence; stale receipts require the documented manual recovery.
  4. If a retained owner lacks a required capability, inspect its connections and review manager retirement. The release-compatible burrow --workspace PATH restart asks before ending that manager and opening the TUI; v0.2.0 also provides the headless workflow.
  5. Reconnect explicitly with saved settings. Re-export chains whose build or resource bindings have changed.

There is no automatic Burrow updater. A stale receipt, unknown socket or incomplete cache publication requires investigation; see troubleshooting. Quit reviews whether to keep or close connections, and retains the Hovel daemon in either case.
