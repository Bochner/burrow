Hovel integration

Burrow uses Hovel’s public SDK and protocol through the single burrow@0.1.0 module for workspace inspection, saved profiles, retained SSH connections and shell lifecycle, forwarding, files, runs, reports and chains. See connection operation and legacy-module transition.

Who owns what?

Burrow frontendTerminal rendering, frontend-local interactive SSH shells, editor and Hovel CLI processes.End with this frontend.

Hovel module stdout belongs exclusively to framed JSON-RPC. The separate Charm frontend owns terminal rendering and local interactive shells; retained modules own SSH connections and runs. Hovel owns workspaces, sessions, confirmations and collected artifacts.

Saved-chain automation uses explicit workspace selection and Hovel's confirmation and launch policy. Connection and tunnel chains either create an explicitly confirmed connection to a running SSH server or consume an exactly selected live tunnel. Tunnel consumption is bounded owner-mediated HTTP, with no transparent arbitrary-module routing or generic Mesh bridge. Markdown reports remain ordinary Hovel artifacts usable outside Burrow.

Current-source session commands create and manage Hovel-retained shells. Headless shared input, resize, independent observation and screen snapshots use public session commands. TUI migration remains planned work; existing interactive TUI shell bytes and resizing stay frontend-local. See resource lifetimes and the generated CLI/base-module reference. Optional MCP is not required for Burrow operator skills, and Burrow exposes no separate REST service or public SDK.
