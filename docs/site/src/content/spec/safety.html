Authorized use and security

Authorized red-team emulation only. Use Burrow in environments you own or are explicitly authorized to assess, with written scope and approvals.

Host trust and credentials

Burrow uses the accepted LazySSH host-trust policy for targets and jump hosts:

StrictHostKeyChecking=no
UserKnownHostsFile=/dev/null

There is no separate host-key approval or retained user trust record. Review the actual SSH command and endpoint before connecting. See authentication and the connection-control decision.

Saved profiles contain settings and file references, not credentials. Hidden CLI prompts keep answers out of arguments and history; literal password arguments can expose them there. Ordinary TUI authentication fields are visible while typing; bare --password and chain authentication use hidden fields.

Operational boundaries

SurfaceBoundary
WorkspacePrivate operational directory, not isolation from other processes running as the same user.
Local toolRuns as the local user without a sandbox. Raw socket commands have no complete per-command Hovel audit.
RunCapture budgets and ordinary-process-group cancellation limits are explicit. Uncollected output can be lost.
Shared shellOne controller arbitrates input; terminal history is memory, not durable evidence or structured completion.
Artifacts and logsMay contain sensitive operational output. Keep the workspace and redirected feeds private.

Runtime loss and older releases

The current runtime pins Hovel v0.4.4 with the SQLite WAL-lock fix. Older v0.1.0 and v0.2.0 Burrow releases used v0.4.2 and carried its concurrent SQLite-access crash limitation. Review active resources before upgrading.

Daemon or module loss does not guarantee remote cleanup, shell recovery or uncollected output recovery. Preserve evidence and follow manual ownership recovery.

Report a vulnerability

Use private GitHub security advisories and follow the security policy. Exclude credentials and third-party target data.
