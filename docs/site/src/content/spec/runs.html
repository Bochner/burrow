Commands and scripts

Run a command or script on an existing SSH connection, inspect its progress and save stdout and stderr as Hovel evidence. The TUI and CLI use the same workflow. Choose how the script reaches the target explicitly: stream its source, pass a small script inline, or stage a private remote file.

A run belongs to a retained Hovel session under the single burrow@0.1.0 module. Prepare it against an explicitly selected live connection, review its command and per-stream storage budget, then launch that same run. Preparing never executes remote code. Repeating launch returns the original run and never repeats its remote action. Leaving the command view, quitting Burrow with Keep running, or losing the launch caller does not cancel it.

Run a script from the TUI

  1. Connect to the target. The examples below assume a live connection named gateway.
  2. Enter local in the management prompt to see the workspace's upload root. Save the example script and any input file there using your local editor. The default is WORKSPACE/burrow-files/uploads; a configured root takes precedence. Script paths start at this root, independently of the file browser's current directory.
  3. Enter one of the run now commands below in the management prompt. Tab completes connection names, script flags, modes and common interpreter paths. Choose the script path and arguments explicitly; there is no separate script-picker dialog.
  4. Review the target, arguments, script and stdin snapshot sizes and hashes, mode, interpreter, output budget, and any staging path, keep setting or timeout. Confirm to launch and collect. Escape cancels the review and leaves a prepared run without executing it.
  5. After collection, press Ctrl+L for Collected output. Read stdout, stderr, the exit outcome and any staging cleanup result. Tab switches to Activity log; Ctrl+L returns to management.

Use run list to find retained IDs, run inspect ID for full details, and run cancel ID to review a cancellation. ID in examples means the actual ID returned for your run. Leaving the view does not cancel execution.

Commands

For a single-command workflow, enter run now gateway -- ps -elf. The connection name selects an already connected target. Burrow prepares a fresh run, inspects its immutable request and presents one review covering launch and collection. Confirming launches that exact run, waits for completion and collects stdout, stderr and the result into Hovel evidence. Open Ctrl+L Results to read the formatted output; Tab switches to workspace activity. A nonzero remote exit still collects output and remains visible as failure.

For explicit approval without a dialog, use run now gateway --yes -- ps -elf. Optional --budget BYTES and Burrow's --yes go before --; everything after it belongs to the remote command. Without --yes, the CLI returns the prepared id, review digest and exact confirm command. That continuation uses run launch ID --collect to wait and collect the same run. Cancelling a TUI review leaves an inert prepared run available to inspect, launch or close. Each new run now invocation creates another run; use the existing ID when retrying. An error after preparation reports the ID to inspect before retrying. Stopping the wait or quitting with Keep running does not cancel remote execution; use run inspect ID and run collect ID to recover its output. The wait has no default deadline, and does not block sibling workspace commands.

Use these commands in Burrow's management prompt or after burrow --workspace /absolute/workspace on the CLI. Tab completes live connection names and retained run IDs. Launch, cancel, collect and close show a review in the TUI; Escape dismisses it without executing the action. CLI review returns a digest: repeat the unchanged command with --review DIGEST --yes to approve. An explicit CLI --yes also confirms without a separate review round trip. The review binds the action, retained ID, exact connection creation, command and budget.

Command arguments are passed literally, including spaces, quotes, empty strings and Unicode. Use an explicit /bin/sh -c when shell expansion or redirection is intended. NUL arguments and invocations over the 64 KiB quoted argument budget are refused. Execution uses the selected existing OpenSSH master, without a remote Python requirement, fresh-login fallback or default execution timeout. A missing or changed master requires a new explicit connection and run.

Commands and arguments are nonsecret inputs: they appear in reviews, process arguments and Hovel's retained requests. Never put passwords, tokens or other secrets in them. Output can itself contain sensitive evidence; keep the workspace private and apply Hovel's artifact retention policy.

The existing workspace operation log records submitted commands and retained execution outcomes. Launch refuses target work when its attempt cannot be saved. Cancellation and close still proceed when logging fails and report that failure. Inspect's auditError preserves a completion-log failure separately from remote exit and output capture. Stream bytes remain in their files and Hovel artifacts, rather than being duplicated into operation notes.

Script source and program input

Use the same prepare/launch or run now workflow for scripts. Local script and standard-input paths resolve inside the workspace's configured upload root; relative paths start there. Traversal, links escaping the root and special files are refused. Preparation creates private snapshots, recording their paths, sizes and SHA256 hashes in the review. Editing the original files afterward does not change the prepared run. Each input is limited to 256 MiB; this is a production snapshot bound, separate from the configurable output budget. Contents are not copied into histories or Hovel request records. A script can itself print sensitive data into captured output.

Example: stream a script with literal arguments

Save this as check.sh in the upload root. It prints each argument exactly as received:

printf '<%s>\n' "$@"

Enter this single line in Burrow's management prompt, then confirm the review:

run now gateway --script check.sh --mode stream --interpreter /bin/sh -- 'My Documents' 'café' '$(hostname)' ''

The collected stdout is:

<My Documents>
<café>
<$(hostname)>
<>

The space, Unicode characters, command-substitution text and empty argument survive unchanged. $(hostname) is printed literally. Everything after -- is a script argument, including text that looks like a Burrow option. Source occupies stdin in stream mode; a script that needs its own input must use inline or stage mode.

Example: supply program stdin without a remote file

Save the following two files in the upload root. The script takes a report name as its first argument and reads independent data from stdin:

printf 'report: %s\n' "$1"
while IFS= read -r item; do
  printf 'item: %s\n' "$item"
done
oak
pine

Keep the final newline in the input file so the shell loop reads both lines. Run the small, nonsecret script inline:

run now gateway --script summarize.sh --mode inline --interpreter /bin/sh --stdin inventory.txt -- weekly
report: weekly
item: oak
item: pine

The script source and stdin are separate: the shell receives the source through -c, while inventory.txt supplies its input stream. Burrow also accepts binary stdin, including NUL bytes; whether those bytes are meaningful depends on your script or program. Inline source is visible in SSH process arguments and must contain no secrets. It is not stored as source text in Burrow's recorded request.

Example: stage the same script explicitly

Use the same files and arguments with --mode stage:

run now gateway --script summarize.sh --mode stage --interpreter /bin/sh --stdin inventory.txt -- weekly

The expected stdout is the same. The review additionally shows an unpredictable remote path under /tmp/burrow-script.*/script. Confirmation creates the private directory, uploads the source, executes it with the chosen interpreter, and attempts cleanup. A successful example reports remoteExit: 0, staging: ready and stageCleanup: removed. Staging is useful when the interpreter needs a filename or the source exceeds the inline limit; Burrow never selects it automatically.

Example: execute an existing remote script

If an administrator has already installed /opt/admin/summarize.sh on the target, invoke it as an ordinary command. Only the optional input file is local:

run now gateway --stdin inventory.txt -- /bin/sh /opt/admin/summarize.sh weekly

Burrow neither uploads nor removes that remote script. Its contents and any changes to it remain the target's responsibility; it is not a local source snapshot.

Use the same workflow from your local shell

Prefix commands with the executable and workspace. These backslash continuations are for your local shell; enter management-prompt examples as single lines. This command prepares and returns a review without starting the script:

burrow --workspace /absolute/workspace run now gateway \
  --script summarize.sh --mode stage --interpreter /bin/sh \
  --stdin inventory.txt -- weekly

Review the returned details, then run its exact confirm command with the same executable/workspace prefix. It launches and collects the prepared ID. Repeating the original run now command prepares another run. To authorize launch and collection directly, include Burrow's --yes before --:

burrow --workspace /absolute/workspace run now gateway \
  --script summarize.sh --mode stage --interpreter /bin/sh \
  --stdin inventory.txt --yes -- weekly

Explicit staging and cleanup

Staging creates a new unpredictable /tmp/burrow-script.*/script path, shown in the prepared review. Its directory is 0700 and its file 0600. Existing paths are refused. Staging uses ordinary Linux shell tools: /bin/sh, mkdir, stat, cat, rm and rmdir, with GNU/BusyBox syntax. It installs no helper or Python runtime. A staging attempt is bounded to eight seconds and cleanup to four seconds; slow or lost acknowledgements remain explicit failures or uncertainty.

By default, completion, nonzero exit and confirmed ordinary-group cancellation remove only the staged file with its acknowledged identity, then its private directory if empty. Replaced files, symlinks and unrelated directory contents are preserved. --keep explicitly retains staging, including after failure or cancellation; it never implies that a script's own file changes are undone. Cleanup verifies the selected master again and never reconnects. Lost execution observation, uncertain ownership or unavailable transport leave cleanup unconfirmed. Stronger process containment and post-loss cleanup recovery remain later work.

Inspect and collected results expose input snapshots, staging, stageCleanup and timedOut alongside remote exit, capture and collection outcomes. A staging failure does not launch the script; retrying that run's launch cannot repeat staging. Prepare a new run explicitly after investigating. Cleanup failures remain visible even when script execution and collection succeeded. Remote staging cleanup is separate from closing the run's private local snapshots and output; registered evidence survives both.

To retain the staged script deliberately, add --keep before --:

run now gateway --script summarize.sh --mode stage --interpreter /bin/sh --stdin inventory.txt --keep -- weekly

The result reports stageCleanup: kept and the reviewed path remains available for manual inspection. This applies after failure or cancellation too. Closing the run removes its owned local working files, not a remote file you explicitly chose to keep.

Observed resultMeaning
remoteExit: 7, stageCleanup: removedThe script failed with exit code 7, and its staged source was removed. Captured stdout and stderr remain collectible.
remoteExit: 0, stageCleanup: failed; …The script completed successfully, but cleanup could not safely remove everything. Inspect the stage path; replaced files and unrelated contents are preserved.
stageCleanup: unconfirmed; …Burrow cannot prove cleanup, for example after master loss. Do not infer that the file was removed or the remote process stopped.

Output and outcomes

Each run captures separate binary stdout and stderr in private 0600 files under a private WORKSPACE/.burrow-run-* directory. The default budget is 256 MiB per stream, visible in every review and configurable at prepare time using a positive byte count. Capture keeps draining independently of terminal views. A budget, write or sync failure marks output incomplete while preserving available bytes and any known remote exit.

run output reads up to 32 KiB from the supplied byte offset and returns data as base64 and nextOffset. Each response includes the same capture snapshot's state, remoteExit, budgetPerStream, storedBytes, receivedBytes, outputComplete and outputError. Byte counts in this response describe the selected stream. Reads neither move another reader's position nor collect evidence. This chunk bound is separate from the storage budget.

Inspect reports the execution state, remoteExit, outputComplete, outputError, and byte counts. The two-element receivedBytes and storedBytes arrays are stdout then stderr. A nonzero remote exit is a known result, independently of collection. SSH exit 255, a missing launch prefix, transport loss and incomplete observation remain transport-or-completion-unknown; Burrow does not invent a remote exit. A successful local SSH stop is not proof of remote termination.

run follow ID [stdout|stderr] [OFFSET] opens an independent live output tab. The default stream is stdout. An explicit nonnegative byte offset resets that stream's preview; otherwise reopening preserves its position and scroll state in this frontend. The same command after burrow --workspace /absolute/workspace opens the viewer from a terminal. For pipes, agents or Hovel operations, use bounded run output reads and retain nextOffset for each stream.

ControlBehavior
Tab / Shift+TabSwitch stdout and stderr, each with its own position.
Arrows, PgUp, PgDn, Home, mouse wheelScroll and pause following. The preview stays still while capture continues and status updates.

F1Open contextual help; Escape restores the same view.

The viewer holds at most 32 KiB of original bytes per stream as its current preview. Its displayed byte range makes omitted earlier output explicit; full captured bytes remain available within the run's storage budget. Viewer positions and previews are frontend memory and end with that frontend. A new frontend can resume from an explicit offset. Each frontend reads independently, and opening, switching, closing or disconnecting a viewer never launches, cancels or collects a run.

All reads run asynchronously, with one request in flight per viewer. Input, help and resize remain usable during output bursts. Control characters, bidirectional controls and invalid binary bytes are escaped for management display; a split UTF-8 character waits for its remaining bytes, and any incomplete final byte is escaped after execution ends. Original capture and collected artifacts are unchanged. The header distinguishes execution status, remote exit and capture completeness, including visible budget/write failures and collectible partial output. “Complete” capture is not collection. Unavailable owners are shown as unverified; viewing never reconnects SSH or starts a replacement run. An older retained owner without the live status response is refused by the viewer; bounded run output remains available.

Cancellation and close

Optional --timeout 30s (or another positive Go-style duration such as 5m) starts at execution launch, after any staging. It requests the same ordinary-group cancellation as manual cancel and records timedOut. A timeout does not prove remote termination: inspect the cancellation and cleanup results. Stopping the foreground wait does not trigger this timeout or cancel a run.

run prepare gateway --script summarize.sh --mode stage --interpreter /bin/sh --stdin inventory.txt --timeout 30s -- weekly
run launch ID
run inspect ID
run cancel ID
run collect ID
run close ID

These are separate lifecycle actions, not a sequence to paste blindly. Replace ID with the prepared run's ID. Launch confirms execution; cancel is needed only while a run is active. Collect saves available output after completion or cancellation, and close releases the working files. The example script normally finishes before 30 seconds; a longer-running script would trigger the requested timeout.

Cancel before launch records cancelled-before-launch. For a running command on Linux, Burrow checks the remote leader's PID, process group and /proc start time over the same master, sends TERM to that ordinary process group and checks for remaining live members. Sibling runs and the shared connection remain available. The result distinguishes observed ordinary-group termination from unconfirmed cancellation. A process that ignores TERM is not silently escalated to KILL.

Identity checks and signalling are not atomic. A mismatched or missing leader, unavailable master, descendants that leave the group, and cleanup after owner loss remain refused or explicitly unconfirmed. This is ordinary process-group cancellation, not a containment guarantee. Targets without compatible Linux process metadata can execute commands, but cancellation cannot establish this identity. Do not infer that every descendant stopped from an ordinary-group result.

Close refuses an active run: cancel explicitly first. Closing removes only the run's original working output; unrelated replacement files or directories are preserved and cleanup uncertainty is reported. It leaves registered Hovel artifacts intact.

Collection and owner loss

After collecting, press Ctrl+L to read the Collected output tab with colored command metadata and separate stdout/stderr previews. Tab switches to the workspace Activity log; Ctrl+L returns. The viewer includes artifacts from closed runs and refreshes when reopened. Previews are limited to 64 KiB per stream with full local paths for the original files. Hovel stores these files under WORKSPACE/artifacts/sha256/.

After completion or cancellation, explicitly collect stdout, stderr and a JSON result through Hovel's FileArtifact and JSON artifact contracts. Partial output is collectible. The CLI reports collection: succeeded only after Hovel has persisted the artifacts. Failed collection does not change the remote exit or remove working files; retry collection against the same ID. Repeated collection creates another Hovel result referencing the retained bytes. Inspect Hovel's artifact inventory using the returned collection runID; the original execution throw remains launchRunID.

Uncollected output can be lost on module or daemon failure. There is no run adoption, automatic relaunch, recovery scan or separate Burrow job database. Abandoned private working directories may remain for manual investigation; their presence does not prove execution or completeness. Successfully registered artifacts follow Hovel retention and survive run close and owner failure.

Local tools

Add --local before -- to run a tool on the daemon host with an explicitly selected connection. See local tools and automation for socket/config context, local exit and cancellation semantics, and working saved Hovel chains.

Hovel interface

The base module's command setting accepts the same run operations and returns structured JSON in the throw result summary. run follow is terminal navigation built on the shared run output operation, not an unbounded protocol stream. Hovel throws require --allow-dangerous. Prepare creates a burrow-run-v1 session. Its typed inspect/output controls observe retained state; launch/cancel controls act on that exact session. Raw privileged session controls are not an independent confirmation mechanism. Use the reviewed Burrow command flow for approvals and collection; its existing workspace dispatch lock serializes collection and close through artifact persistence.
