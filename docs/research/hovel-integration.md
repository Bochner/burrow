# Hovel integration research

Research baseline: 2026-09-11; Hovel source commit `c461ba282a8aecc7aa3a079a4613bf5e2640c388`. Findings below come from the checked-out source and its first-party documentation. Recommendations and spikes are proposals, not claims of implemented Burrow functionality.

## Recommendation

Keep `Bochner/burrow` independent and ship a Hovel **ModulePackage**, implemented against the public Go SDK. In Hovel, this package is the native extension mechanism: the SDK and a packaged module work together. There is no need to choose between an SDK integration and a module/plugin. Keep SSH operations usable without terminal rendering so the same implementation can support structured Hovel runs and a Charm interface. This is a proposed architecture; the external SDK build and terminal spikes below must validate it before the rewrite.

| Option | What it means | Decision |
| --- | --- | --- |
| Independent repository, Go SDK module | Hovel launches Burrow as a subprocess speaking its module protocol; normal install/discovery/session/audit paths apply. | Recommended first integration. |
| In-process Go plugin or patch to Hovel CLI | A different extension mechanism or direct dependency on Hovel internals. | No documented requirement or supported native plugin API found for this. Avoid. |
| Separate Charm frontend for Hovel | Burrow calls the daemon HTTP/JSON API to operate Hovel-owned workspaces, runs and sessions. | Supported architectural direction; consider after the module and terminal spike. |
| Standalone SSH app | Burrow owns its connection lifecycle directly. | Can serve homelab use with shared SSH code, but does not itself establish Hovel integration. |

Hovel's module guide explicitly covers private/out-of-tree packages and linked development installs. Its frontend guide requires frontends to share daemon application services and states that `hovel tui` is currently unimplemented. Hovel's agent plugins are integrations for coding agents, not an SSH module loading mechanism. Sources: [module development](https://github.com/vibepwners/hovel/blob/c461ba282a8aecc7aa3a079a4613bf5e2640c388/docs/site/src/content/spec/module-development.html), [frontends](https://github.com/vibepwners/hovel/blob/c461ba282a8aecc7aa3a079a4613bf5e2640c388/docs/site/src/content/spec/front-ends.html), [agent integration installer](https://github.com/vibepwners/hovel/blob/c461ba282a8aecc7aa3a079a4613bf5e2640c388/core/internal/infra/agentintegration/installer.go).

## Actual module and session contracts

`hovel.Module` requires `Info()`, `Schema()` and `Run(*hovel.Context)`. The first two are cheap, side-effect-free catalog operations. The current module types are `survey`, `exploit`, and `payload_provider`; there is no `ssh` or general `management` module type. Proposed classification: non-mutating SSH inventory as survey behavior, command/session behavior following Hovel's existing execution/module conventions, with the exact package/step split decided during the PRD. Do not add a private module type. [Module types and interface](https://github.com/vibepwners/hovel/blob/c461ba282a8aecc7aa3a079a4613bf5e2640c388/sdk/go/hovel/module.go).

`hovel.Serve` owns stdin/stdout for Content-Length-framed JSON-RPC. Progress belongs in `ctx.Log`, which emits structured `module/log` notifications; a Bubble Tea renderer must never write ANSI output to module stdout. `Context.Input` resolves per-run inputs, then target configuration, then chain configuration. Results distinguish outputs, findings, artifacts, sessions, and installed payload descriptors. An SSH login does not constitute an installed payload. [Server](https://github.com/vibepwners/hovel/blob/c461ba282a8aecc7aa3a079a4613bf5e2640c388/sdk/go/hovel/server.go), [context](https://github.com/vibepwners/hovel/blob/c461ba282a8aecc7aa3a079a4613bf5e2640c388/sdk/go/hovel/context.go), [results](https://github.com/vibepwners/hovel/blob/c461ba282a8aecc7aa3a079a4613bf5e2640c388/sdk/go/hovel/result.go).

An interactive SSH connection can implement `Session`: `Open`, `Write`, `Read(wait)`, `Close(reason)` and `Closed`. Register it with `ctx.OpenSession`; the SDK attaches the reference to the result. Sessions outlive `Run`, with Hovel retaining the module process. Session transports accept byte chunks, so adapting SSH channel I/O is a closer fit than using `LineShellSession`, whose example implements a local newline-command dispatcher. Connection ownership must therefore move to the session rather than a `defer client.Close()` in `Run`. [Session implementation](https://github.com/vibepwners/hovel/blob/c461ba282a8aecc7aa3a079a4613bf5e2640c388/sdk/go/hovel/session.go), [context lifecycle](https://github.com/vibepwners/hovel/blob/c461ba282a8aecc7aa3a079a4613bf5e2640c388/sdk/go/hovel/context.go), [working example](https://github.com/vibepwners/hovel/blob/c461ba282a8aecc7aa3a079a4613bf5e2640c388/modules/examples/go/mock_exploit_session/main.go).

There is also `PTYSession{Frontend: func(io.Reader, io.Writer) error}`, which runs a local frontend on a pseudo-terminal and exposes its bytes to Hovel. This is a promising way to attach the Burrow UI inside a Hovel session. However, the implementation is Linux-only; other platforms return an unsupported error. The session interface and dispatcher have no resize operation at this revision, and the local PTY allocator does not initialize a window size. A production full-screen TUI needs an explicit sizing/resizing investigation. A local PTY is distinct from requesting a PTY on the remote SSH server. [PTY adapter](https://github.com/vibepwners/hovel/blob/c461ba282a8aecc7aa3a079a4613bf5e2640c388/sdk/go/hovel/pty_session.go), [Linux allocator](https://github.com/vibepwners/hovel/blob/c461ba282a8aecc7aa3a079a4613bf5e2640c388/sdk/go/hovel/pty_linux.go), [other platforms](https://github.com/vibepwners/hovel/blob/c461ba282a8aecc7aa3a079a4613bf5e2640c388/sdk/go/hovel/pty_unsupported.go).

The dispatcher handles requests concurrently, ignores notifications including `cancel`, and waits for outstanding requests before processing shutdown. `hovel.Context` is not a standard Go `context.Context`. Proposed implementation requirement: bounded SSH dial/handshake/command operations, explicit session cleanup, bounded output buffering, and lifecycle tests for close/disconnect. Do not infer automatic cooperative cancellation from the SDK's context name. [Server lifecycle](https://github.com/vibepwners/hovel/blob/c461ba282a8aecc7aa3a079a4613bf5e2640c388/sdk/go/hovel/server.go).

## Mesh and credentials

For SSH forwarding through existing Hovel nodes, use Hovel's Mesh bridge contract. The daemon binds a loopback endpoint and forwards it to a provider stream. `NewMeshBridgeEndpoint` plus `DialMeshBridge` handles the capability preface and returns a connection suitable for an SSH handshake. The endpoint capability is an in-memory secret. If Burrow later exposes SSH-connected nodes and forwarding to other modules, implement only the optional Mesh interfaces required, initially description and stream operations rather than the whole provider surface. The daemon, not every provider, owns local Mesh bridge binding. Long-lived provider listeners need a lifecycle durable beyond a single RPC subprocess. [Mesh architecture decision](https://github.com/vibepwners/hovel/blob/c461ba282a8aecc7aa3a079a4613bf5e2640c388/docs/adr/0001-use-mesh-for-node-operations.md), [Mesh interfaces](https://github.com/vibepwners/hovel/blob/c461ba282a8aecc7aa3a079a4613bf5e2640c388/sdk/go/hovel/mesh.go), [bridge helper](https://github.com/vibepwners/hovel/blob/c461ba282a8aecc7aa3a079a4613bf5e2640c388/sdk/go/hovel/mesh_bridge.go).

Hovel requirements support secret fields and the SDK contains credential material wrappers and credential-provider interfaces. These do **not** establish that it already provides a general SSH-password/key vault. The documented daemon credential selector path currently describes certificate DER, SPKI and PKCS#8 projections for workspace PKI. SSH passwords, encrypted OpenSSH private keys, agent sockets and SSH user/host certificates require their own mapping spike. Secret marking/redacted formatting is not proof of encrypted persistence. Keep credentials out of results, artifacts, command history, errors and UI transcripts; prefer agent/key references where practical and verify where Hovel persists configuration before enabling password storage. [Requirement schema](https://github.com/vibepwners/hovel/blob/c461ba282a8aecc7aa3a079a4613bf5e2640c388/sdk/go/hovel/module.go), [credential delivery types](https://github.com/vibepwners/hovel/blob/c461ba282a8aecc7aa3a079a4613bf5e2640c388/sdk/go/hovel/credential_delivery.go), [daemon credential contract](https://github.com/vibepwners/hovel/blob/c461ba282a8aecc7aa3a079a4613bf5e2640c388/docs/site/src/content/spec/daemon-rpc.html).

## Package and frontend boundary

A Hovel package is a `.tgz` containing `hovel-module.yaml` with `apiVersion: hovel.dev/v1alpha1`, `kind: ModulePackage`, metadata, `runtime.protocol: jsonrpc-stdio`, and platform-selected launch commands. Platform selectors describe the **operator host**, not the remote SSH target. Handshake/schema remain authoritative; the manifest is launch/install metadata. Development uses `hovel module install --link /absolute/package/root`. Package launches must point at real built executables; do not publish a nonfunctional manifest during research. [Packaging and install specification](https://github.com/vibepwners/hovel/blob/c461ba282a8aecc7aa3a079a4613bf5e2640c388/docs/site/src/content/spec/module-development.html).

A separate Burrow TUI would call HTTP POST JSON methods under `/hovel.daemon.v1.DaemonService/`, described by the checked OpenAPI 3.1 document. This is separate from module JSON-RPC. The existing Go client lives under `core/internal/adapters/daemonrpc`, so importing it from Burrow is not a supported public SDK route. A small client for the required methods or a generated client from the contract is a proposal to test. Prefer the owner-protected Unix socket; the documented TCP mode is plaintext and defaults to restricted read-only access, not a remote authenticated control plane. [Daemon contract](https://github.com/vibepwners/hovel/blob/c461ba282a8aecc7aa3a079a4613bf5e2640c388/docs/site/src/content/spec/daemon-rpc.html), [OpenAPI](https://github.com/vibepwners/hovel/blob/c461ba282a8aecc7aa3a079a4613bf5e2640c388/docs/site/spec/reference/daemon-rpc.openapi.json).

The public import path is `github.com/vibepwners/hovel/sdk/go/hovel`, backed by a public Bazel target `//sdk/go/hovel:hovel`. However, neither the repository root nor `sdk/go` has a `go.mod`; `core/go.mod` declares `github.com/vibepwners/hovel` while the SDK is physically outside `core`. Therefore this checkout does not establish normal standalone `go get` consumption. The SDK BUILD file also loads Hovel's branch-coverage rule, so copying that BUILD file alone is insufficient. [SDK BUILD](https://github.com/vibepwners/hovel/blob/c461ba282a8aecc7aa3a079a4613bf5e2640c388/sdk/go/hovel/BUILD.bazel), [workspace Go files](https://github.com/vibepwners/hovel/blob/c461ba282a8aecc7aa3a079a4613bf5e2640c388/go.work.bazel), [core module](https://github.com/vibepwners/hovel/blob/c461ba282a8aecc7aa3a079a4613bf5e2640c388/core/go.mod).

Proposed first build spike: pin the full Hovel source archive/commit as an external Bazel dependency, then compile a tiny Burrow module against its public SDK target. Measure whether consuming Hovel's Bzlmod module activates unrelated extensions/toolchains. If unsuitable, test a pinned archive with a minimal Burrow-owned BUILD overlay for SDK sources and its `x/sys/unix` dependency, preserving upstream source and license. Prefer a maintainer-supported external SDK distribution if one becomes available. Do not silently vendor and modify SDK code or fabricate a published Go version.

Only adopt build machinery applicable to Burrow: root `MODULE.bazel`, `.bazelversion`, `BUILD.bazel`, minimal `.bazelrc`, Aspect tasks, pinned Go dependency manifests once needed, and lockfiles generated by real resolution. Hovel's remote cache URLs, CI cache modes, C/C++/Rust/Python toolchains and full repository task suite serve its monorepo and are not requirements for a Go SSH module. Inspect and adapt, rather than copying its complete configuration.

## Spikes before committing to the full rewrite

1. **External build:** compile/test the smallest SDK module from Burrow's independent workspace and record the exact pin/overlay and clean-checkout commands.
2. **Real package lifecycle:** linked package discovery, schema validation, one localhost SSH operation, session attach/detach/close and module shutdown without leaked sockets/processes.
3. **Terminal:** Bubble Tea on explicit PTY input/output, terminal size, resize propagation, raw mode, Ctrl-C, detach and no-color behavior. Decide local PTY UI versus separate daemon frontend from evidence; document operator OS limits.
4. **Credential custody:** trace secret config persistence, agent availability under the daemon, encrypted key prompting, host-key verification and changed-key handling. Hovel workspace PKI and SSH trust must not be conflated.
5. **Mesh:** reuse one existing Mesh bridge for an SSH handshake; only then determine whether Burrow must additionally act as an SSH Mesh provider.

These are implementation acceptance gates. This research does not claim that an external SDK build, Hovel package install or live SSH session has already passed.
